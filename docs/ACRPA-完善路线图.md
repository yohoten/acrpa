# ACRPA 完善路线图 —— 功能 · 软件设计 · UI 设计

> 版本基线：`v0.1.29-beta` · HEAD `9555be6`（"拆分 ACRPA.py 第一阶段：Mini Bar 出模块"）
> 代码规模：`src/` 53 个模块 / 约 35,500 行 · 6 个超 75 KB 的巨型模块
> 分析方式：静态通读 + AST 统计 + 实机执行验证。所有 P0 结论均已在源码中复核。

## 0. 结论先行

ACRPA 的**功能 breadth 已经相当完整**——68 条命令、OCR/浏览器/AI/NetLink/市场/调度齐全，且 `script_package`、`paddle_dll`、`netlink/security` 三个子系统的工程严谨度明显高于同类个人项目。

真正制约它从"能用的 beta"走向"可信的生产工具"的，不是功能数量，而是**四笔结构性欠账**：

| 欠账                           | 表现                                                                                                 | 后果                                                                  |
| ------------------------------ | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **① 确定性缺陷未收敛**  | 找图缓存类型不一致、DD 驱动无视开关、预发布版本比较失效                                              | 旗舰命令（找图/点图）在缓存命中时必崩；用户显式关闭的内核驱动仍然加载 |
| **② 结构不可测试**      | `import ACRPA` 即构建 `Tk()` 并启动定时器；6 个 75–245 KB 上帝模块                              | 引擎控制流测试被 CI 误判跳过 → 缺陷可长期静默存在                    |
| **③ 脚本格式无 schema** | 表头`命令类型`/`操作` 并存、空值 `""` 与字面量 `"None"` 混用、四处硬编码 `range(2, nrows)` | 无迁移路径、静默丢首行、`"None"` 泄漏为真实参数                     |
| **④ UI 是过程式单体**   | ACRPA.py 5,738 行 / 0 个类 / 88 个模块级控件全局量 / 40 处`global`                                 | 每个改动都是全局编辑；主题靠"嗅探中文文案"反推语义色                  |

**建议的投入顺序**：先修 ①（1–2 天，收益立竿见影），再做 ② 的第一刀（应用入口 + 事件总线，约 1 周，解锁后续所有重构），④ 按模块逐步拆（已有 Mini Bar 的成功先例），③ 与功能扩展并行推进。

## 2. P0 —— 已验证的确定性缺陷（建议立即修）

以下 7 项均已逐行复核，非推测。

### P0-1 找图缓存返回 `tuple`，调用方按 `Point` 取值 → **缓存命中必崩**

```python
# src/engine.py:845   —— 缓存命中返回普通元组
                return (x, y)
# src/engine.py:916,920 —— 调用方按属性访问
                    pa.click(loc.x, loc.y, ...)
```

`_find_cached` 的 docstring（engine.py:832）明确声明"Returns pyautogui Point object (with .x/.y attributes)"，实现与声明不一致。缓存未命中时返回 `loc`（真 Point）正常，**命中时抛 `AttributeError: 'tuple' object has no attribute 'x'`**。

- 影响面：`找图 / 区域找图 / 点图 / 区域点图` 四条旗舰命令，在 5 秒 TTL 内的重复搜索必崩。
- 旁证：`acrpa_api.find_image:189-196` 同时处理了两种形态，证明该不一致是疏漏而非设计。
- 附带缺陷：缓存键仅用 `img_path`（engine.py:837），忽略 `confidence / region / grayscale` —— 区域限定搜索会被全屏命中污染；`_image_cache` / `_CACHE_ORDER` 为跨线程模块全局量且**无锁**（engine.py:212-215）。
- **修法**：返回 `pyautogui.Point(x, y)`；缓存键改为 `(img_path, confidence, region, grayscale)`；加 `threading.Lock`；补一条缓存命中的回归测试。

### P0-2 DD 内核驱动无视用户开关，仍然加载并使用

```python
# src/engine.py:1018  —— 无条件获取并使用
        dd = get_dd_backend()
        if dd and dd.enabled and mode in ["auto", "direct"]:
```

`state.INPUT_MODE` / `state.USE_DD_DRIVER` 由 `settings_window.py:590` 写入，但在 `engine.py` 中**零处读取**（已 grep 确认）。`config.json` 中 `use_dd_driver: false`、`input_mode: "sendinput"`，而命令默认 `mode="auto"`（engine.py:1008-1010）恰好落在 DD 可用集合内，`DDBackend.__init__` 还会自动搜索 DLL（dd_backend.py:68-69）。

- 后果：用户明确关闭的内核态驱动实际仍在生效——正确性缺陷 + 杀软/反作弊误报 + 合规风险。
- 附带：`_find_dd_dll`（dd_backend.py:103-108）把 `os.getcwd()` 纳入 DLL 搜索路径 → 经典 DLL 植入面；加载前无哈希/Authenticode 校验。
- **修法**：`engine.py` 中读取 `INPUT_MODE`/`USE_DD_DRIVER` 做门禁；参照 `paddle_dll.py:906` 的**子进程预检**模式隔离崩溃；DLL 搜索限制在安装目录内并校验哈希。

### P0-3 预发布版本号解析为 `0.0.0` → 市场更新检查永久失效

```python
# src/script_package.py:73-87
def version_tuple(v):
    ...  # "0.1.29-beta".split(".") → int("29-beta") 抛异常 → 列表清空 → 补零 → (0,0,0)
```

`marketplace.check_update` 使用 `version_gt`（marketplace.py:489）。当前版本正是 `0.1.29-beta`，因此**市场更新检查对当前版本恒定返回"无更新"**。

- **修法**：委托给 `updater.compare_versions`（已正确处理 prerelease），或统一版本比较器（见 §7-重复实现）。

### P0-4 引擎控制流测试被 CI 误判为"GUI 冒烟"而跳过

```python
# tools/run_tests.py:51-52
if name.startswith(GUI_PREFIXES):      # GUI_PREFIXES = ("_smoke_",)
    return "GUI 冒烟: 需要真实窗口会话 (本机全量回归时用 --all)"
```

`tools/_smoke_engine.py`（180 行，覆盖 如果/嵌套如果/条件循环/循环+如果/嵌套循环/跳出循环）**只 import `state`、`engine`、`scriptdata`，不需要窗口**，实测 9/9 通过、exit 0，却被前缀规则排除。

- 后果：§2 中 P0-1 自 commit `b19b493` 起长期存在而未被发现，正是此缺口所致。
- **修法**：改按**文件内容/依赖**判定而非文件名前缀；或显式维护一份 CI 白名单，把 `_smoke_engine.py` 纳入。

### P0-5 停止执行是"建议性"的 —— `_chk()` 返回值被全部丢弃

```python
# src/engine.py:822-827
    def _chk(self):
        if state.quit2: return False
        ...
# 调用处：engine.py:892, 953, 962, 968, 989, 1053 … 均为裸语句 self._chk()
```

`_chk()` 实际只充当**暂停闸门**；`quit2` 置位后当前命令仍会跑完。真实中断点仅在 engine.py:337（行间）、:649（循环迭代间）、:1591、:1810。

- 后果：用户点"停止"无法打断 20 秒的找图超时、30 秒的 Python 块或长 `等待`。
- **修法**：`_chk()` 返回 `False` 时向上抛出统一的 `AbortSignal`；或在 `等待`/`_image_search_loop`/`py_sandbox` 中分段检查。

### P0-6 脚本保存非原子，失败即截断且无备份

```python
# ACRPA.py:2157 / :2199 —— 直接写用户目标路径
                wb.save(fp)
# :2164-2169 —— 版本快照在保存之后写入，且失败被吞
```

无临时文件 + `os.replace`、无 `.bak`、无保存前快照。磁盘满或 Excel 占用文件时，用户脚本被截断且无前像可恢复。

- 反差：`script_package.py:552-593` **已经正确实现了**"临时目录解压 + `os.replace`"的原子安装——编辑器自身的保存路径反而更脆弱。
- **修法**：复用 `script_package` 的原子写模式；保存前先落版本快照。

### P0-7 三个"看得见但不起作用"的设置项

| 配置项                             | 写入处                            | 读取处                                                |
| ---------------------------------- | --------------------------------- | ----------------------------------------------------- |
| `recording_stop_hotkey`          | settings_window.py:1377/1388/1400 | **无** —— 停止热键硬编码在 ACRPA.py:5670-5677 |
| `ocr_preload`（启动时预热）      | settings_window.py:727            | **无**                                          |
| `input_mode` / `use_dd_driver` | settings_window.py:590            | **无**（见 P0-2）                               |

用户改了设置、界面显示成功、实际行为不变——这类"静默无效"对信任度的伤害远大于功能缺失。**修法**：要么接线，要么从 UI 移除。

## 3. 软件设计 —— 四个结构性瓶颈与拆解路线

### 3.1 导入期即构建应用 → 彻底不可测试

```python
# src/ACRPA.py:755
root = tkinter.Tk()
# :5513-5514  root.after(100, _periodic)     —— 导入即启动 100ms 轮询
# :5694        root.after(200, _hotkey_poll)
# :5716-5718  NetLink 启动
# run.py:57   from ACRPA import root; root.mainloop()
```

`src/` 下**没有任何 `if __name__ == "__main__"` 守卫**（仅 `dd_backend.py:391` 有一个无关的）。`import ACRPA` 会建窗口、起定时器、启动调度器。

**这是所有其他重构的前置阻塞项。** 必须先落地：

```
src/app.py     # 薄入口：main() 内构建 root、装配依赖、mainloop
src/ACRPA.py   # 退化为纯定义模块（可被 import 而无副作用）
```

`help_window.py` / `help_content.py` 是仓库中**结构最好的一对文件**——真实类、调色板与字体依赖注入、`_load_content → _load_commands → _build → _load_nav` 分阶段、内容与渲染彻底分离、`scaled()` 用了 46 次（全库最多）、零硬编码颜色。**这是应当复制到全库的范式。**

## 4. 数据模型 —— 最大的一笔技术债

### 4.1 现状

- 内存模型 `ScriptData`（scriptdata.py:5-44）= **1 个命令名 + 恰好 9 个位置字符串参数**，全字符串化，无类型、无 ID、无启用位、无注释列、断点不落盘。
- 磁盘格式是**遗留的位置式 Excel**，且内部不一致：

| 问题                               | 证据                                                                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 表头文字不稳定                     | `命令类型`（间隔点击.xls）vs `操作`（脚本模板.xls）；两个文件第 0 行还是自由文本说明                                                  |
| 空值两种编码                       | `""` 与字面量 `"None"` 并存；**只有** `ai_enhance.py:676-756` 做了归一化，引擎所有命令都不处理 → `"None"` 会成为真实参数值 |
| 四处硬编码跳过前 2 行              | `ACRPA.py:2051`、`ACRPA.py:652`、`workflow.py:50`、`snippets.py:147` —— 无表头嗅探，只有 1 行表头的脚本会静默丢掉首条命令       |
| `templates.py` 传 8 个参数       | templates.py:79 等，与 9 参数约定不符                                                                                                     |
| `ScriptData.COMMANDS` 导入期冻结 | scriptdata.py:6 —— 插件命令永远不出现在其中                                                                                             |

- **无 schema 版本、无魔数、无迁移路径**。对比：`.acrpapkg` 是全项目唯一有真正版本化 schema 的东西（`SUPPORTED_MANIFEST_VERSIONS`，script_package.py:39）。

### 4.2 建议：引入 `.acrpas`（JSON）作为一等格式

```json
{
  "schema": 1,
  "id": "uuid",
  "name": "间隔点击",
  "created": "2026-10-03T20:00:00+08:00",
  "meta": { "app_min": "0.2.0", "author": "", "desc": "" },
  "rows": [
    { "id": "r1", "cmd": "按键", "enabled": true, "comment": "",
      "args": { "key": "down", "times": 1, "interval": 0.1 },
      "breakpoint": null }
  ],
  "vars": {}, "images": ["btn_ok.png"]
}
```

要点：

1. **具名参数**替代 9 个位置参数 —— 命令 schema 层（`commands.py` 的 `_parse_params`/`schema`/`validate`，已存在且设计良好）可直接驱动校验与 UI 表单。
2. **稳定行 ID** —— 解决 §3.4 的索引耦合，也让断点/注释可持久化。
3. **`schema` 字段 + 迁移函数表** —— 为未来任何格式演进留门。
4. **保留 `.xls` 双向兼容**：`xls → JSON` 导入器（复用现有 4 处解析逻辑，合并为唯一实现）+ `JSON → xls` 导出。Excel 仍可作为一个编辑入口，但不再是唯一真相。
5. 顺带解决：`"None"` 归一化、表头嗅探、模板 8/9 参数不一致。

> 这一步是**后续所有功能扩展的前置条件**：断点续跑、diff/版本对比、脚本市场增量更新、AI 结构化生成，都依赖稳定的行身份。

### 5.1 增量 A：交互架构——把"轮询 + 全局布尔"换成显式状态机

当前运行态散落在 `state.running` / `state.pause_event` / `state.quit2` / `state.quit3` / `engine._script_failed` 多个布尔与事件里，由 10Hz 轮询反推 UI。建议定义一个显式运行态机：

```
idle → validating → running ⇄ paused → stopping → finished
                       ↓                              ↑
                    failed ───────────────────────────┘
```

- 每个状态迁移触发事件，UI 订阅后更新；删除 `_periodic` 中的四态按钮手搓机（ACRPA.py:5415-5425）。
- 收益：暂停/继续/单步/停止的语义清晰，"单步"目前是 200ms 定时器（ACRPA.py:3514-3516），换成真状态机后可做真正的单步。

### 6.2 让录制"回放得住"

录制目前只产出绝对像素 `坐标`，无图像/OCR 锚点 —— 换分辨率、移窗口、换机器即失效。建议：

1. **多锚点录制**：一次点击同时记录「图像模板裁剪 + 窗口相对坐标 + OCR 文本 + 绝对坐标」，回放时按可靠性顺序回退（图像 → OCR → 相对 → 绝对）。
2. **文本合并**：连续按键合并为 `输入`/`写入` 命令（当前逐字符回放，固定 0.1s 间隔）。
3. **接上已实现但未接线的采集器**：`_record_scroll`、`_record_window_activate`、`_record_screenshot` 三个 helper 存在但**事件路径从不调用**（滚轮钩子根本没装）。
4. **录制时截图**：每个动作附一张裁剪图，直接作为后续找图的模板，形成"录制即产出资产"的闭环。

### 6.3 调试器

### 6.4 命令生态与插件

- **插件子系统当前实际是死代码**：`plugins/__init__.py:38` 跳过 `_` 前缀文件，而示例插件就叫 `_example_plugin.py` —— 实机验证 `list_plugins() == []`，文档中承诺的 3 条示例命令从未加载；加载器本身还被 `engine.py:2014` 的静默 except 包裹。
  **修法**：改名启用 + 补启动测试断言"示例插件必须加载成功"。
- **插件是任意代码、启动即执行、零门槛**（plugins/__init__.py:37-49）。建议引入显式启用清单 + `PLUGIN_API_VERSION` + 清单文件。
- **handler 契约不统一**：必须同时处理 `row.args` 和 `row[i].value` 两种形态（ai_enhance.py:669-678），无版本协商；`list_plugins` 靠**函数身份**反查（plugins/__init__.py:79-85），装饰器包装后即失效。
- `commands.get_handler` 是 O(n) 线性扫描（commands.py:116-119），且插件可静默遮蔽内建命令 —— 建议改为 dict + 命名空间 + 重复名拒绝。

### 6.5 无头 / CLI（打开新场景）

`run.py` 只做依赖检查后 `mainloop`。核心层其实已近乎无头（`utils.log1` 在无 `_tlog` 时优雅降级，`py_sandbox` 刻意不引入 GUI），只是没人接线。建议：

```
acrpa.exe --script foo.acrpas [--headless] [--var k=v] [--json-report out.json] [--exit-code]
```

价值：CI 集成、服务器定时批处理、NetLink 远端执行、以及——**让端到端自动化测试成为可能**。

### 6.6 AI 能力的可信化

- `AIAnomalyDetector` 声称后台执行（ai_enhance.py:404-405），实际在**调用线程同步运行**，timeout=90s，每 10 条命令或失败率 >0.2 触发一次 → 脚本卡顿最多 90 秒。
- AI 输出**无校验、无边界检查**：`ai_find_element` 直接 `int(result["x"])` 后 `pa.click(x, y)`（:197-198、:692），幻觉坐标会点击屏幕任意位置。建议 JSON schema 校验 + 坐标钳制到屏幕范围 + 解析失败重试一次。
- 无重试/退路/熔断：`APIRateLimitError` 从未被捕获重试，失败即静默 no-op（"点这个按钮"这一步悄悄没发生）。
- 两套模型注册表不一致（UI 下拉用 `MODEL_REGISTRY`，provider 层用 `PROVIDER_PRESETS`，两者几乎不重叠）；Anthropic 是死路（`openai_compatible: False` 但 `create_client_active` 仍会发 OpenAI 格式请求）。
- **数据出境无脱敏**：全屏截图 base64 上传，变量与日志原文序列化 —— 脚本若输入过密码，该值会随变量一起发给第三方。建议：上传前脱敏 + 显式确认 + 允许"仅本地"模式。

## 11. 工作流编排 —— 从"加了箭头的列表"到真正的控制流图

> 本章解决一个具体问题：当前"流程图"在数据结构上**根本不是图**。参考控制流图（CFG）重建模型、布局与交互。

### 11.1 现状诊断：它不是图，是列表

数据模型是**数组 + 嵌套树**，没有任何边：

```python
# src/ACRPA.py:4308
_wf_data = {"name": "未命名工作流", "steps": []}
# 嵌套：parallel.steps / loop.steps / condition.then / condition.else
```

渲染是**单列纵向布局**，`x` 恒为常量：

```python
# src/ACRPA.py:4592
        x = 20
# :4634      y += _NODE_GAP
# :4637-4642 箭头只连 i → i+1
```

所以那些箭头是**数组下标的视觉装饰**，不承载任何控制流信息。直接后果：

| 结构                         | 数据中存在           | 图上可见       | 后果                                                              |
| ---------------------------- | -------------------- | -------------- | ----------------------------------------------------------------- |
| `condition` 的 then / else | 有                   | **否**   | 分支节点与顺序节点外观完全相同，条件只显示为一行文字（`:4570`） |
| `loop` 的循环体范围        | 有                   | **否**   | 只有"↻ 3次"文字（`:4574`），看不出哪些步骤在循环内             |
| `parallel` 的多个分支      | 有                   | **否**   | 只有"N子步骤"计数（`:4568`）                                    |
| 跳转 / 汇合                  | **模型不支持** | —             | 无法表达"失败重试三次后走告警分支"这类真实需求                    |
| 节点坐标                     | **不持久化**   | —             | 布局每次由索引推导，用户无法整理与保存                            |
| 执行路径                     | —                   | 仅当前节点边框 | 看不出这次运行走的是哪条分支                                      |

交互层面同样缺失：滚轮只有 `yview_scroll`（`:4300-4303`），**无缩放、无横向平移、无框选、无多选**；拖拽只移动被拖节点、其他节点不让位、无插入指示线，松手后全量重绘（`:4689-4690`、`:4720`）；**无连线操作**（不能建边、断边、改分支目标）；**无 undo/redo**；导出截图只能截可见区域（`:5114-5130` 依赖 `winfo_rootx/winfo_width`）；无 minimap。

### 11.2 为什么 CFG 是正确的模型

控制流图的每个概念都能在 ACRPA 里找到对应物，且每一项都换来了实际能力：

| CFG 概念              | ACRPA 对应物                                     | 换来的能力                         |
| --------------------- | ------------------------------------------------ | ---------------------------------- |
| 基本块 Basic Block    | 一个步骤节点（script/command/wait/variable/log） | 布局与分析的原子单位               |
| 边 Edge               | 显式`edges[]`                                  | 任意跳转、分支、汇合               |
| 入口 / 出口           | 开始 / 结束节点                                  | 可达性分析的起点与终点             |
| 双出口条件节点        | `condition` 的 true / false 端口               | 分支在图上真实可见                 |
| 回边 Back Edge        | 指向**支配**自己的节点的边                 | 自动识别循环，无需手写 loop 节点   |
| 自然循环 Natural Loop | 回边 + 被支配节点集合                            | 自动框出循环体范围                 |
| 支配关系 Dominator    | 必经节点                                         | 识别循环头、公共前置、可合并的分支 |
| 强连通分量 SCC        | 循环簇                                           | 嵌套/多重循环的边界                |
| 不可达节点            | 从入口 BFS 不到                                  | **"这个步骤永远不会执行"**   |
| 环路复杂度 E−N+2P    | 流程复杂度指标                                   | 超阈值提示拆分                     |

关键差别在于：**不可达检测、循环识别、路径枚举这三项是"只要图模型建起来就自动获得"的能力**，不需要额外设计。而当前模型下它们无法实现——因为边根本不存在。

### 11.3 一个关键洞察：脚本与工作流是同一个 CFG 的两个粒度

脚本内部的 `如果 / 否则 / 结束如果`、`循环开始 / 循环结束`、`跳出循环` **本身就是一套 CFG**。§2 审计中的三个缺陷，本质都是"用线性扫描模拟图"付出的代价：

| 缺陷                                                                | 根因                           |
| ------------------------------------------------------------------- | ------------------------------ |
| `如果` 递归用切片（engine.py:597-608）导致行号变成切片相对        | 没有节点 ID，只能靠位置        |
| `循环` 内联执行**完全不更新行状态**（:664-684），进度条冻结 | 循环没有出口节点可更新         |
| `跳出循环` 在 `如果` 块内静默 no-op（:744-745）                 | 没有"跳到循环出口节点"的边语义 |

若统一模型：每行是一个节点，`如果` 是双出口菱形，`循环开始/结束` 构成回边，**执行变成在图上遍历**——行号、进度、断点、单步全部天然正确，断点成为节点属性而不再依赖行索引（与 §4 的稳定行 ID 完全同构）。

**建议**：脚本 = 命令级 CFG（细粒度，节点是一条命令）；工作流 = 脚本级 CFG（粗粒度，节点是一个脚本或子流程）。两者共用同一套图模型、布局算法、静态分析器与执行遍历器。这是本项目最值得做的一次抽象收敛——两份实现变成一份，且脚本编辑器可以顺带获得流程图侧栏。

### 11.4 目标数据模型

```json
{
  "schema": 2,
  "name": "订单处理",
  "graph": {
    "nodes": [
      {"id":"n1","type":"start","x":340,"y":40,"w":120,"h":32},
      {"id":"n2","type":"script","x":340,"y":112,"w":200,"h":40,
       "data":{"path":"login.xls"},"comment":"","enabled":true},
      {"id":"n3","type":"condition","x":340,"y":192,"w":120,"h":56,
       "data":{"expr":"${count} > 0"}},
      {"id":"n4","type":"script","x":180,"y":288,"data":{"path":"retry.xls"}},
      {"id":"n5","type":"parallel","x":420,"y":288,
       "data":{"branches":["a.xls","b.xls"]}},
      {"id":"n6","type":"script","x":340,"y":384,"data":{"path":"notify.xls"}}
    ],
    "edges": [
      {"id":"e1","from":"n1","from_port":"out","to":"n2","to_port":"in"},
      {"id":"e2","from":"n2","from_port":"out","to":"n3","to_port":"in"},
      {"id":"e3","from":"n3","from_port":"true", "to":"n4","to_port":"in","label":"是"},
      {"id":"e4","from":"n3","from_port":"false","to":"n5","to_port":"in","label":"否"},
      {"id":"e5","from":"n4","from_port":"out","to":"n3","to_port":"in","back_edge":true}
    ]
  }
}
```

**向后兼容是硬约束。** 存量 `.json/.yaml` 工作流必须能打开：

- **提升（树 → 图）**：`steps[i]` 建节点 + 边 `i → i+1`；`condition` 展开为菱形 + 两个分支子图 + 汇合节点；`parallel` 展开为并行容器；`loop` 展开为范围框 + 回边。
- **降级（图 → 树）**：反向编译回 `steps` 数组，供 `workflow.py` 的 `_execute_step` 继续使用。

> **关键工程判断：不要把执行引擎改成图解释器（至少不要在第一期做）。** `workflow.py` 的树形递归执行器已经能工作，且被 NetLink、调度器、`运行工作流` 命令多条路径依赖。正确做法是**图只作为编辑视图与静态分析源，保存时降级为树执行**——风险最低，且立刻拿到 90% 的收益。图解释器放到最后一步（分期 F），届时它只是遍历器的另一种实现。

### 11.5 布局算法选型

采用 Sugiyama 分层框架的简化版，自上而下（符合现有纵向心智）：

| 步骤        | 算法                                                        | 参数 / 说明                                            |
| ----------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| 1. 去回边   | DFS 三色标记（白/灰/黑）                                    | 灰节点上的边即回边，暂存并标记`back_edge`            |
| 2. 分层     | Kahn 拓扑 + 最长路径分层`level(n) = max(level(pred)) + 1` | 保证边只跨相邻或更下层                                 |
| 3. 层内排序 | 重心法（barycenter），迭代 4 轮                             | 取前驱/后继平均位置排序，显著减少交叉                  |
| 4. 坐标分配 | 中位数启发式（median heuristic）                            | 层内保持最小间距`NODE_GAP`；容器节点先定尺寸再排内容 |
| 5. 回边路由 | 三次贝塞尔曲线，走左右侧通道                                | 与正向边区分：虚线 + 循环色；避免穿越节点区            |

**性能边界**（明确写出，避免后期踩坑）：

- 支配关系用迭代数据流算法，O(n²)；n < 500 时单次 < 10 ms，可接受。
- 布局**仅在结构变更时重算**；拖拽、平移、缩放不触发重算（只做变换）。
- Canvas item 数 > 400 时启用视口裁剪，只渲染可见区域内的 item。
- 分支/循环容器先递归布局子图，再作为原子节点参与外层布局。

### 11.8 CFG 静态分析面板 —— 差异化能力

这是 CFG 化之后**几乎免费获得、却是同类工具普遍没有**的能力。建议在画布下方做一个可折叠的"检查"面板：

| 检查项       | 算法                                   | 呈现                                     |
| ------------ | -------------------------------------- | ---------------------------------------- |
| 不可达步骤   | 从入口 BFS，未被访问                   | 节点红色描边 + 列表"步骤 5 永远不会执行" |
| 孤立节点     | 入度 = 0 且出度 = 0                    | 列出并建议连接或删除                     |
| 悬挂出口     | 分支未汇合且未达出口                   | 提示"分支 X 没有汇合点"                  |
| 死循环风险   | 存在回边但循环体内无修改循环变量的节点 | 警告 + 定位回边                          |
| 循环无退出   | SCC 内不存在指向 SCC 外的边            | 严重警告                                 |
| 缺少终止节点 | 图无 exit 节点                         | 提示                                     |
| 路径爆炸     | 枚举入口→出口路径数 > 阈值（建议 64） | 提示拆分或改用变量驱动                   |
| 环路复杂度   | `E − N + 2P`                        | 数值徽标，> 15 提示拆分                  |

**路径枚举**还有第二个用途：生成 dry-run 用例。"你的工作流有 6 条可能路径，其中 2 条从未被执行过" —— 这是 RPA 场景里非常实际的提醒。

### 11.9 执行可视化

CFG 视角独有的价值是**一眼看出这次跑的是哪条路**：

- 当前节点脉冲高亮（替代现有的一次性边框重绘）
- **走过的边加粗染色并累计计数**，标签显示"×3"
- **未走过的路径整体淡化至 30%** —— 这是当前模型做不到的
- 分支命中率持久化到工作流文件的 `stats` 字段，跨运行累积，供 §11.8 的"从未执行的路径"使用
- 执行结束后可回放：按时间轴重放走过的边

| **G. 脚本级 CFG**       | 脚本编辑器接入同一模型，命令级流程图侧栏；顺带修复 §2 的行号/进度/跳出循环缺陷     | 高                 | F            |

**风险与控制**：

- A/B 期**完全不动执行路径**，可独立发布，即使 C 期出问题也不影响现有用户。
- E 期全是纯函数（输入图、输出问题列表），是**全项目最容易写单测的部分**，建议优先补测试（呼应 §8）。
- F 期是最大风险点，涉及执行语义变更。建议先做成"实验开关"，与树执行器并存，跑通后再切换默认。
- G 期依赖 §4 的 `.acrpas` 行 ID，应排在其后。

## 12. 可选依赖插件化 —— paddleocr / opencv / playwright 的外置与按需安装

> 本章解决一个具体问题：如何让重量级可选依赖（OpenCV 图像匹配、Playwright 浏览器自动化、PaddleOCR 文字识别、DD 内核驱动）**不进主包**，又能被普通用户一键装上启用。

### 12.1 先澄清一个判断：代码已经拆好了，缺的是"能装上"

调研后的第一个结论可能与直觉相反——**这些模块在代码层面已经是可插拔的**，真正缺失的不是"剥离"，而是"分发"。四条证据：

| 事实 | 证据 |
| --- | --- |
| 依赖清单里本来就没有它们 | `requirements.txt` 只有 9 个轻量包（pyautogui / Pillow / pyperclip / xlrd / xlwt / requests / urllib3 / certifi / pywin32），cv2、playwright、paddleocr 一个都不在 |
| 已经严格懒加载 | `browser_backend.py:49-50` 把"不得触发 playwright 导入"写进模块契约；:`110`/`:140`/`:1260` 三处 import 全在函数体内；未安装时静默降级（`:134-136`） |
| 打包时明确排除 | `ACRPA.spec` 的 `excludes` 已排除 `numpy`/`numpy.*`/`cv2`/`cv2.*`/`opencv_python` 等约 120 项 |
| 成品体积证明了这一点 | `dist/ACRPA.exe` = **14.7 MB**（`ocr_backend.py:22` 自己写的"总计约 230 MB，不会打包进 ACRPA.exe"已成立） |

因此本章的目标应准确表述为三件事：

1. **把「你自己去 pip install」变成「点一下装」** —— 当前 `browser_backend.py:136` 给用户的提示是 `pip install playwright && playwright install chromium`。对一个面向非编程用户的 RPA 产品，这条路径等于不存在。
2. **把「不知道装没装」变成三态可查** —— 现在四处 probe 逻辑各写各的，没有统一的能力协商。
3. **把「记着别 import」变成 CI 门禁** —— `excludes` 是手工维护的，任何人加一句顶层 `import cv2` 防线就失效且构建不报错。

#### 层 1：Capability 三态

现在四处重复实现同一件事：

- `engine.py:188` `_has_cv2()` → bool
- `browser_backend.py:104` `_check_playwright_available()` → bool
- `ocr_backend.py:42` `_check_paddle_available()` → bool
- `ocr_backend.py:205` / `dd_backend` 的 `enabled` 属性

统一为：

```python
# src/extensions/registry.py
class CapState(Enum):
    READY    = "ready"      # 可用
    MISSING  = "missing"    # 未安装
    BROKEN   = "broken"     # 装了但自检失败（DLL 缺依赖 / 模型不全 / ABI 不符）
    DISABLED = "disabled"   # 用户显式关闭

@dataclass
class Capability:
    id: str                      # "cv.match" / "browser.playwright" / "ocr.paddle_dll" / "input.dd"
    label: str
    ext_id: str | None           # 由哪个扩展提供；None = 主包内置
    degraded: Literal["hard", "soft", "none"]   # 见 §12.7
    degraded_note: str
    probe: Callable[[], ProbeResult]           # 必须便宜、幂等、无副作用
```

**为什么是四态而不是布尔**：因为 UI 上给用户的下一步动作完全不同——

| 状态 | UI 呈现 | 用户动作 |
| --- | --- | --- |
| `READY` | ✔ 已就绪 | 禁用 |
| `MISSING` | ○ 未安装 | **安装** |
| `BROKEN` | ⚠ 不可用（缺 `paddle_inference.dll`） | **修复 / 重装** |
| `DISABLED` | ⏸ 已禁用 | **启用** |

布尔值只能给出"装/没装"，把 BROKEN 和 MISSING 混为一谈正是当前 paddle_dll 依赖诊断困难的原因。

**约束**：`probe()` 不得超过一次 import + 一次轻量自检；native 自检必须走**独立子进程**（沿用 `paddle_dll.py:891` 已有的子进程预检思路），避免一次 Access Violation 打死整个应用。结果写入 probe 缓存，`sys.importlibs` 不存在则用布尔标志位。

#### 层 2：命令声明依赖（收益最高的一步）

`commands.py` 的 `register(name, desc, params, handler, schema=None)` 增加一个可选字段：

```python
commands.register("找图", "在屏幕上查找图片", "图片名, 精度(默认0.96)",
                  handler, requires=("cv.match",))
```

`commands.py:36-44` 已经确立了良好的向后兼容取舍（`list_all()` 仍返回四元组，20+ 处消费方不用改），加字段沿用同一策略即可。

这一步之所以收益最高，是因为**一次声明、四处生效**：

| 消费方 | 改造前 | 改造后 |
| --- | --- | --- |
| 命令表格 / 命令库 UI | 未装依赖的命令照常显示，运行才报错 | 未就绪命令显示角标，点击直接进安装面板 |
| dry-run 运行前校验（阶段二） | 只能查参数类型 | 能提前报出"第 12 行需要未安装扩展" |
| CFG 静态分析（§11 E 期） | — | 新增一条检查规则：**不可满足的命令节点** |
| 帮助窗口 | 命令表里无依赖信息 | 自动生成"依赖：OpenCV 图像匹配扩展"（与 `tools/_gen_help_command_table.py` 联动） |

#### 层 3：不要新写下载器

分发所需的三块基建**已经全部存在**，正确做法是收敛而不是重写：

| 能力 | 现成实现 | 拿来做什么 |
| --- | --- | --- |
| GitHub Release 取直链 + sha256 | `updater.py:203` `_pick_release_asset()`（能吃 asset 的 `digest` 字段） | 扩展包的分发渠道 |
| 双栈下载 + 体积/哈希校验 | `marketplace.py:344` `_download_file()` + `:320` `_verify_download()`（requests→urllib 回退） | 安装器的传输层 |
| ZIP 安全解压 + 原子落地 | `script_package.py:264` `_is_within()` / `:276` `_safe_member()` / `:300` `_is_symlink()` / `:308` `_check_limits()` | **zip-slip、软链接、文件数上限防护直接复用** |

新建 `src/extensions/`：

```
extensions/

  registry.py       # Capability 注册表 + 三态模型
  manager.py        # 安装/卸载/启用/禁用/修复
  index.py          # 内置的白名单清单（见 §12.6 信任模型）

```

### 12.4 安装布局与加载机制

目录根放在 **`%LOCALAPPDATA%/ACRPA/extensions/`**，不用项目内的 `lib/` —— 后者是打包资源目录，会被 PyInstaller 的 `datas` 扫描吞掉，正是 DD DLL 被误打包的原因。

```
%LOCALAPPDATA%/ACRPA/extensions/
├── installed.json                 # 已安装登记表（id / version / 启用状态 / 安装时间）
├── quarantine/                    # 校验失败件的隔离区（不删，便于排查）
└── <ext_id>/<version>/
    ├── extension.json             # 清单（版本/变体/提供的 ability/依赖）
    ├── pure/                      # 纯 Python 包 → 注入 sys.path
    ├── native/                    # DLL → os.add_dll_directory()
    ├── models/                    # 模型权重（可与 DLL 分离分发）
    └── browsers/                  # 仅 playwright 用
```

#### 为什么用 sys.path 注入而不是 pip

ACRPA 以 **PyInstaller onefile** 形态发布（`dist/ACRPA.exe` 14.7 MB），用户机器上**既没有 pip，也没有可用的 Python 解释器**。因此"让玩家 pip install"在分发形态下不可行。

可行路径是纯路径注入：opencv-python 的 wheel 解压后就是一个 `cv2/` 目录，放进 `pure/` 再 `sys.path.insert` 即可直接工作，无需任何安装工具链。

**代价必须写清楚**：这是强 ABI 绑定。cp312 编译的 `cv2` 不能被 cp311 加载。因此清单必须携带变体维度：

```
addon-<ext_id>-<version>-<platform>-<arch>-<python_tag>.zip
例：addon-cv.match-1.0.0-win-amd64-cp312.zip
```

索引发布时需要为每个受支持的 Python 版本各出一个变体；加载时按 `sys.version_info` 精确匹配，不匹配直接报 `BROKEN(ABI 不符)`，不做"猜一个试试"。

#### Native DLL 加载必须处理的一个坑

Python 3.8+ 起 Windows 的 DLL 搜索路径不再包含 PATH 和当前目录。`ctypes.CDLL("PaddleOCR.dll")` 即使 DLL 在旁边，也会因为找不到同目录的 `paddle_inference.dll` / `tbb12.dll` / `yaml-cpp.dll` / `opencv_world470.dll`（`paddle_dll.py:52` 已列出）而失败。

正确做法 `paddle_dll.py:441-503` **已经实现**，此处固化为规范：

```python
# paddle_dll.py:441
def _add_dll_dir(d):
    if hasattr(os, "add_dll_directory"):
        return os.add_dll_directory(d)      # ← 返回的 cookie 必须持有到 DLL 卸载之后

# paddle_dll.py:503
self._cookie = _add_dll_dir(self.dll_dir)   # 存在实例字段上，防止被 GC 后搜索路径失效
```

**持有 cookie 这一条必须写进审核清单** —— cookie 被垃圾回收后搜索路径会静默失效，症状是"有时能用有时不能"，极难排查。

#### Playwright 的特殊处理

它不能走 `sys.path` 注入：浏览器二进制由 CLI 下载到固定位置、约 **150 MB**、且路径写在编译期的 registry 里。两条路：

- **首选（离线可控）**：预打包 Chromium zip，解压到 `native/browsers/`，启动前设 `PLAYWRIGHT_BROWSERS_PATH` 指向该目录。这是 Playwright 官方支持的环境变量，干净且不会污染用户主目录。
- **兜底（需联网）**：保留 `playwright install chromium`，但必须在 UI 里带进度条并明确标注体积，不能像现在这样只在日志里给一句提示。

#### PaddleOCR 的方向性建议：优先原生 DLL，而非 Python 包

| 方案 | 体积 | ABI 风险 | 行为可控性 | 现状 |
| --- | --- | --- | --- | --- |
| Python `paddleocr` | ~230 MB（含 numpy + inference binary） | 严格 | 模型自动下载行为不受控 | `ocr_backend.py:42-105`，已惰性单例 |
| `PaddleOCR.dll` | 884 KB DLL + 模型 | **无**（原生） | 原型可配置 + 崩溃隔离 | `paddle_dll.py`，封装最严谨 |

建议把 **DLL 方案作为默认 OCR 后端推广**：`paddle_dll.py` 已经具备"初始化原型表 + 子进程崩溃隔离 + 失败不抛异常"三项能力，是全项目可选后端里封装最好的。它在体积、ABI 稳定性、行为可预测性上全面占优，唯一门槛是需要自建模型目录——而这正好可以由 §12.3 的扩展安装器来承担（DLL 与模型分离分发，模型可单独替换）。

### 12.5 安装流程

`install(ext_id)` 的十个步骤，其中 4、5、7 三步是新增的加固：

1. 取远程索引 → 得到版本/变体列表/URL
2. 按 `(platform, arch, python_tag)` 选定变体，不匹配则拒绝（不猜）
3. 流式下载到 `*.part`，支持 `Range` 断点续传
4. **强制 sha256 校验**（见 §12.6 —— 这是吸取 updater 教训的关键项）
5. ZIP 安全解压，复用 `script_package._is_within` / `_safe_member` / `_is_symlink` / `_check_limits`
6. 原子落地：先解到 `.tmp-<rand>`，成功后再 `os.replace()` 到目标目录
7. **安装期自检（新增）**：起子进程跑 `probe()`，失败则整体回滚到第 1 步之前的状态，并把产物移入 `quarantine/`
8. 写 `installed.json`
9. 提示需重启应用后生效（`sys.path` 已冻结，见下方注意）
10. 生命周期其余动作：`disable` = 移出加载路径（**需重启**）；`uninstall` = 删目录；`repair` = 重跑 4–7

> **注意：enable / disable 无法热插拔。** 依赖已进入 `sys.modules` 后再移 `sys.path` 不生效。UI 上应明示"下次启动生效"，或提供"重启应用"按钮，不要给用户即时生效的错觉。

**把「崩溃隔离」前置到安装期**是这里最有价值的一处时序调整：`paddle_dll.py` 的子进程预检本来是在**运行时**做的（第一次调用前），改为在安装完成瞬间做。这样用户在安装面板里就能看到"自检通过 / 自检失败原因"，而不是等到跑脚本失败才发现问题。这不是新发明，是把项目里已有的正确做法挪到更早的位置。

### 12.6 信任模型 —— 必须比 marketplace 更严

当前 marketplace 的问题是「有完整性、无真实性」：索引项同时含有 `url`（`marketplace.py:69`）和 `sha256`（`:67`）两个字段，**两者都来自同一个下载下来的 JSON**。攻击者只要同时提供文件和匹配的哈希，就能通过全部校验 —— 校验在此等价于没有。

`updater.py:262` 的注释其实已经写明了正确原则：

> `sha256 取 asset 的 digest 字段... 绝不能回填本机 VERSION 里的值 (那描述的是已安装的旧包)`

把同一原则严格应用到扩展上：

```
远端索引  ── 只提供：id / 版本 / URL / 体积 / 最低应用版本 / 变体列表
内置清单  ── extensions/index.py，随 ACRPA 二进制分发：id → {version: sha256}
```

**远端只能回答"有什么"，不能回答"它是什么"。** 哈希白名单必须随程序本体发布，安装时以内建值为准，远端提供的哈希一律忽略（或仅用于交叉告警）。

可选增强（阶段三）：对白名单本身做 code-sign / PGP 签名。

### 12.7 降级契约 —— 一个必须修的 P0

这是本章唯一涉及正确性而非架构的条目。

```python
# engine.py:959
if _has_cv2():
    ...                     # 走 confidence 灰度匹配
else:
    # engine.py:965-967
    if not _cv2_hint_logged:
        _cv2_hint_logged = True     # ← 只打一次 hint，然后静默降级为精确匹配
    ...
```

用户在脚本里填了「精度 0.96」，系统没有 cv2 时**该参数被静默忽略**，执行且不报错。这属于「能跑但行为不对」，比直接崩溃更难排查——用户会以为自己在做灰度匹配，实际在做精确匹配。

修法，配合 `Capability.degraded` 三档：

| `degraded` | 语义 | 缺失时的行为 |
| --- | --- | --- |
| `hard` | 影响**正确性** | 命令**失败**，报错："命令『找图』需要扩展『OpenCV 图像匹配』，点此安装" |
| `soft` | 只影响**精度/性能** | 首次执行时一次非模态提示 + 每次日志 warning + 写入运行报告 |
| `none` | 无降级路径，缺失即不可用 | 同 `hard`（命令失败） |

**建议 `cv.match` 定为 `hard`**：用户既然显式指定了精度，系统就不该返回一个不满足该精度的结果。若产品侧坚持保持可用性，也应升级为明确的对话框确认，而非仅一次日志。

这条改动约 10 行代码，却是本章对用户体验影响最直接的一项。

### 12.8 CI 门禁 —— 把手工纪律变成自动化保证

当前防线是 `ACRPA.spec` 中手工维护的约 120 项 `excludes`。任何人在任何模块顶层加一句 `import cv2`，防线立刻失效，**而构建不会报错**。

建议新增 `tools/_check_spec_excludes.py`：构建后读取产物 TOC，断言下列模块不在包内——

```
cv2 / cv2.* / numpy / numpy.* / paddle* / playwright / torch / scipy
matplotlib / greenlet / pyee / opencv_python
```

并入 `tools/run_tests.py` 与 GitHub Actions，**构建失败即阻断**。

这是本章投入产出比最高的一条：几行代码，把"记得别 import"变成"不可能打包进去"。它同时消解了 CV/AI 能力扩张时的长期风险——随着 §6 功能路线推进，误引入重依赖只是时间问题。

### 12.10 明确不做成扩展的

| 依赖 | 理由 |
| --- | --- |
| **Pillow** | 36 处引用，UI 工具栏图标依赖 `ImageTk` 渲染，**构建期**就要用 |
| **pyautogui** / **pywin32** | 核心输入模拟链路，`engine.py` 主路径必需 |
| **requests** / **urllib3** / **certifi** | 更新器与市场本身要用——扩展安装器依赖它们，循环依赖 |

**判断标准（建议写进贡献规范）**：凡是在 **UI 构建期**而非**命令执行期**被首次用到的依赖，留在主包；只有那些"只有少数命令需要、且默认不需要"的能力才外置。

`browser_backend.py:215` 把 locator 解析层做成纯函数（仅 stdlib）、`:1508` 把 codegen→DSL 转换器做成纯 stdlib，正是这一标准的优秀实践——**先把纯逻辑剥离到无依赖层，再把有依赖的调用收窄到函数体内**，这个 pattern 值得在全库推广。
