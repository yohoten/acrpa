P0-1（原第 8 条）工作流「变量管理」弹窗崩溃
----------------------------------------------------------------------
[已完成]

现象
  点击工作流工具栏「变量管理」后无反应；控制台/日志出现
  NameError: name 'sp' is not defined（src/ui/workflow_view.py 约 2652 行）。

根因
  sp（DPE 尺寸换算函数）此前是 build() 内的局部变量；抽取到 ui/workflow_view.py 后，
  只有 build() 内部定义了局部 sp，_wf_open_variable_manager() 里直接引用 sp(...)，
  该函数作用域没有 sp，且模块级也没有兜底，于是首次点击即抛 NameError。
  同类风险：后续新增弹窗若忘记取 sp，会重复踩坑。

方案
  在 _wf_open_variable_manager() 入口用注入值取一次，并做可调用兜底：
      sp = _CTX.get("sp")
      if not callable(sp):
          sp = lambda v: float(v)
  这样：有注入 → 与其它弹窗同一套 DPI 换算；无注入（单测/未初始化）→ 1:1 像素，不崩。

改动点
  src/ui/workflow_view.py  _wf_open_variable_manager()

验收
  1) 实机构建后打开弹窗不抛异常（已用脚本验证 dialog_ok）。
  2) tests/_test_workflow_view_split.py 全绿（75 项通过）。

风险 / 后续
  风险极低。后续凡新建弹窗统一从 _CTX 取 sp，或抽一个模块级 _sp(v) 帮助函数，
  避免再次出现「局部变量泄漏到嵌套函数」的问题。

P0-2（原第 1 条）日志自动保存到 logs
----------------------------------------------------------------------
[部分完成]

现状（先确认，避免重复造轮子）
  · ThreadSafeLog 按天写 logs/acrpa_YYYYMMDD.log；
  · crashlog 写 logs/crash_YYYYMMDD.log，并挂 faulthandler / excepthook / threading 钩子；
  · state.log_dir() 已处理便携模式（userdata/logs）与普通模式（程序目录/logs）。
  结论：主链路日志本来就是自动保存的，原记录的真实缺口是「GUI 回调异常不进日志」。

真实缺口（按影响排序）
  G1 Tk 回调异常只打 stderr：Tk 默认走 root.report_callback_exception，
     打包版无控制台，用户只看到「点了没反应」，日志与 crash 文件都没有；
     上面 P0-1 的 NameError 就属于这一类。
  G2 启动早期（日志系统就绪前）的异常只靠 crashlog 兜底，主日志无上下文。
  G3 没有「打开日志目录」入口，用户找不到日志文件。

本次方案（G1）
  在 crashlog 增加 install_tk_hook(root)，把 Tk 回调异常转交 handle_exception(..., "tk-callback")，
  落 crash 文件 + log1 摘要；随后仍调用原钩子，保证终端/开发者能看到完整栈（不吞异常）。
  app._finish_build() 拿到 root 后安装，异常安全（任何失败都不影响启动）。

改动点
  src/crashlog.py  install_tk_hook()
  src/app.py      _finish_build() 中安装钩子

后续（按顺序，均为小改）
  G2-1 在 utils 增加 _EARLY_LOG 环形缓冲（最多 200 条）：日志系统就绪时一次性回放；[已完成]
  G2-2 启动阶段异常（before ui_build）写 logs/startup_error.log，避免与 crash 文件混在一起。[已完成]
  G3-1 在「帮助 / 关于」添加「打开日志目录」（os.startfile(state.log_dir())）；[已完成]
  G3-2 增加「保留最近 N 天」清理（默认 30 天，删除 acrpa_/crash_ 两类，不动 history.jsonl）。[已完成]

验收
  1) 人为在按钮回调里 raise ValueError：logs/crash_当天.log 出现 tk-callback 段，主日志出现 error 摘要；
  2) 正常启动/退出不新增 crash 文件；
  3) 便携模式下所有文件落在 userdata/logs。

风险
  钩子幂等、异常全包，风险低；注意不要替换掉原钩子（本实现是链式调用）。

P1-2（原第 2 条）工作流以流程图展示，且不能是「单列」
----------------------------------------------------------------------
[已完成]

现象
  工作流步骤一多（如 15~30 步的线性流程），流程图区就是一根很长的竖直单列，
  需要不停滚轮/拖动，横向大片空白。

根因
  ui/flow_canvas.layout() 用分层算法：每个「层」横向排开、层内纵向排列。
  纯线性工作流每一层恰好只有 1 个节点 → 每层 1 列 → 视觉上就是单列。
  算法本身没错，缺的是「长链的折行策略」。

方案
  在 layout() 增加蛇形折行（boustrophedon）：
  · 触发条件：层数 > max_rows 且每层节点数 ≤ 1（纯链）；
  · 列数 cols = ceil(n / max_rows)，行数 rows = ceil(n / cols)；
  · 第 1 列自上而下、第 2 列自下而上，相邻列首尾相邻，连线最短；
  · 返回画布尺寸按 cols × rows 计算，滚动区域随之为「宽而矮」；
  · max_rows=0/None 可关闭折行（保留原来的单列竖排，作为回退开关）。
  默认 MAX_ROWS = 8（约一屏半高度）。

改动点
  src/ui/flow_canvas.py  MAX_ROWS 常量 + layout() 折行分支

验收
  1) 20 节点线性图：cols=3（每列 7 行），width=748 / height=644，不再是一根长条；
  2) 分支/并行图（某层 >1 节点）不受影响，仍走原分层布局；
  3) tests/_test_flow_graph.py（58 项）与 tests/_test_flow_canvas_interact.py（19 项）全绿。

风险 / 后续
  · 回边（loop）在折行后可能跨列较长，后续可按 back_edge 单独走外侧通道；
  · 下一步建议（按收益排序）：
    a) 节点内文本自动换行：详情超过 1 行时按宽度截断为 2 行 + 「…」，避免撑破节点；
    b) 分支节点对齐：同层多节点的高度对齐 + 汇聚点居中（现在按中位线，长分支会偏）；
    c) 缩放适配：fit_to_view 后按列数自动选择「纵向优先 / 横向优先」；
    d) 折叠：连续 5 步以上的「同类型命令」折叠为一个组节点，双击展开。

P1-5（原第 5 条）运行调试栏与工作流的耦合
----------------------------------------------------------------------
[已完成]

现象
  · 工作流工具栏有一套「循环/最长」Spinbox，顶部运行栏也有一套，两处都能改；
  · 改运行栏的循环次数对工作流不生效（工作流仍按自己变量里的 1 次跑）；
  · 运行栏选「无限」时，工作流侧只当成 1 次，语义不一致。

根因
  · 工作流工具栏的 wf_loop_var 是独立新建的 StringVar，只有 wf_maxmin_var 与运行栏同源；
  · _wf_run() 用 int(get()) 解析，遇到「无限/自定义…」直接 ValueError 回退 1；
  · workflow.run_workflow() 把 loop_count 归一为 max(1, n)，无法表达无限。

方案
  · 删除工作流工具栏重复的循环/最长 Spinbox，改为一行提示「循环 / 最长: 跟随上方运行栏」；
  · wf_loop_var 直接复用运行栏的 loop_count_var（ACRPA 构建时注入 exec_loop_var），
    wf_maxmin_var 继续复用 exec_maxmin_var —— 两个参数全局只有一份真源；
  · _wf_run() 解析支持「无限」（i18n 文案）→ loop_count = 0；其它非数值回退 1；
  · workflow.run_workflow() 约定 loop_count <= 0 为无限循环（用 itertools.count），
    日志显示「循环: 无限」「第 n/∞ 次」，仍受「最长分钟」与停止按钮约束。

改动点
  src/ui/workflow_view.py  工具栏简化 / 变量复用 / _wf_run 解析
  src/workflow.py          loop_count 容错 + 无限循环 + 日志文案
  src/ACRPA.py             注入 "exec_loop_var": loop_count_var

验收
  1) 运行栏把循环改为 3，工作流实际跑 3 轮（日志 第 1/3…3/3）；
  2) 运行栏选「无限」，工作流持续运行，点停止或到最长分钟退出；
  3) ACRPA.wf_maxmin_var is ACRPA.exec_maxmin_var 仍成立（既有实机断言）；
  4) 工作流工具栏不再出现第二个循环输入框。

风险 / 后续
  · 若某入口只构建工作流而未构建运行栏，exec_loop_var 缺省会回退到默认 StringVar("1")，不崩；
  · 后续可让运行栏在「工作流 Tab」显示当前工作流名与「将执行 N 步」，
    并把工作流「变量管理」入口也提升到运行栏（真正做成上下文工具条）。[已完成]

  步骤：先加只读访问器（不删除旧键）→ 各视图逐步切换 → 最后删旧键。
