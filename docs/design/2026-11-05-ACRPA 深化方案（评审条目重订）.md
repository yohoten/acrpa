# ACRPA 深化方案 v2（基于评审条目重订）

> 版本：2026-11-05
> 输入：评审条目 8/9/10（生态与协议）、二（稳定性）、三（规模化）、工作流完善、AI 深化
> 本方案对条目做三件事：① 用代码实证校准现状 ② 排出**依赖关系**与**先后** ③ 标注每项的**实现落点**与**风险**。
> 结论先行：不要按条目顺序做，要按「地基 → 稳定性 → 规模化 → 生态与 AI」四期推进。

---

## 0. 一句话路线

**先打地基（断言 + run_id + 命令元数据），再做稳定性（元素库 + 自愈 + 断点续跑），然后规模化（作业中心 + NetLink 编排），最后才是生态与 AI（MCP / 插件 UI / function-calling）。**

理由：后面三层几乎全部建立在前面的三样地基上。没有 `run_id`，断点续跑和失败现场无从谈起；没有命令元数据，AI function-calling、工作流校验、沙箱审计都要各自重复造一遍；没有断言，"跑完了"永远不等于"跑对了"。

## 1. 依赖关系（重订的核心）

```
                        ┌─────────────────────────────────────┐
  【地基】              │  A3 命令元数据升级                    │
                        │  group/icon/outputs/side_effect/     │
                        │  idempotent                          │
                        └──────┬──────────┬──────────┬────────┘
                               │          │          │
                               ▼          ▼          ▼
                        E1 AI function-  D 工作流    沙箱审计
                           calling         静态校验
                        ┌─────────────────────────────────────┐
                        │  D5 统一 run_id                       │
                        └──────┬──────────┬──────────┬────────┘
                               │          │          │
                               ▼          ▼          ▼
                        B4 断点续跑    C2 作业中心   失败现场
                          UI                          回放/对比
                        ┌─────────────────────────────────────┐
                        │  B1 元素库                            │
                        └──────────────┬──────────────────────┘
                                       ▼

```

**读法**：箭头上方是下方的**前置**。这就是为什么 A3 / D5 / B1 必须最先做——它们不是功能，是**其它功能的前提**。

## 2. 分层条目（含代码实证）

### A. 战略层：生态与协议

#### A1. 扩展点：从「只能注册命令」到「插件即应用」

**现状**：`core/event_bus.py` 已存在内部实现；插件目前只能往 `commands.py` 注册命令，UI 层（工具栏/右键/设置卡/面板）无法扩展。

**方案**：把 `event_bus` 上升为**对外、版本化的主题契约**（`acrpa.events.v1`），并开放 5 类 UI 扩展点：

| 扩展点 | 注册方式 | 落点 |
|---|---|---|
| 工具栏按钮 | `plugin.register_toolbar(btn_spec)` | `ui/editor_view.py` 工具栏构建后调用插件钩子 |
| 右键菜单 | `plugin.register_context_menu(...)` | 命令表格 / 工作流树的右键菜单构建处 |
| 设置卡 | `plugin.register_settings_card(build_fn)` | `ui/settings/cards/` 已有 `CARD_KEY` 注册机制，直接复用 |
| 独立面板 | `plugin.register_panel(...)` | 主窗口 notebook 或独立 Toplevel |
| 事件订阅 | `event_bus.subscribe(topic, fn, version="v1")` | 已有 `core/event_bus.py` |

**关键约束**：契约必须**版本化**（`v1`），且**加载顺序在 UI 构建之后**——否则插件找不到挂载点。事件主题先冻结一小批（`run.started` / `run.finished` / `run.failed` / `script.saved` / `theme.changed`），不要一开始全开放。

**风险**：低。event_bus 是现成的，主要工作是「定契约 + 写文档 + 给示例插件」。

#### A2. 对外协议：MCP Server / Webhook（战略级）

**现状**：约 94–96 条命令 + 工作流已具备执行层、CLI（`--json-report` / `--exit-code`）、审计（`history.jsonl`）。缺的只是协议适配层。

**方案**：双向。
- **ACRPA 作 MCP Server**：把命令与工作流暴露为标准 MCP tool，让 Claude / Cursor / 自建 Agent 直接调用「点这个窗口 / 跑这个流程 / 取这个 OCR 结果」。
- **ACRPA 作 MCP client**：脚本里新增「调用 MCP 工具」命令，让脚本具备「调 API / 查知识库」能力。

**落地顺序（重要）**：**先只读、后写入**。
1. 第一批只暴露**只读工具**（`ocr_read` / `get_state` / `list_workflows` / `run_history`）——零副作用，安全验证协议链路；
2. 第二批才开放**执行类工具**（`run_script` / `run_workflow` / `click`），且必须走已有的 `failure_policy` + 审批（危险命令挂人工确认）。

**为什么这是护城河**：2026 年 RPA 与 Agent 融合最自然的位置，就是「让 Agent 有一双可靠的手」。纯 GUI RPA 做不到这一点，ACRPA 恰好有执行层 + CLI + 审计三件套，只差协议皮。

**风险**：中。协议适配不难，难在**权限与审计**——必须复用 NetLink 已有的 `required_perm` 分级思路，不能裸奔。

#### A3. 命令元数据升级（地基）

**现状**：分组靠 `res/help/command_groups.json` 外挂（`_fallback_title: 其他命令`，插件命令一律落兜底组）；出参靠 `commands.py:486` 的 `_set_var` 惯例。

**方案**：在 `register()` 上扩展元数据：

```python
@register(
    name="找图",
    group="locate",            # 喂命令面板分组（替代外挂 json）
    icon="🔍",
    outputs=[("found", "bool"), ("x", "int"), ("y", "int")],  # 喂 AI 提示词 / 校验
    side_effect="ui",          # read | ui | disk | network
    idempotent=False,          # 喂工作流校验（写盘命令进 loop 要警告）
)
def cmd_find_image(...): ...
```

**一次改动喂饱四方**：① 命令面板分组（`command_groups.json` 可退役为「从元数据生成」）② AI 提示词自动生成（`outputs` + `side_effect` 直接进 prompt）③ 工作流静态校验（`side_effect=disk` 且 `idempotent=False` 的命令放进 loop 要警告）④ 沙箱审计。

**落点**：`commands.py` 的 `register()` 装饰器 + `command_schema.json` 生成器。
**风险**：低，但**工作量大**（94–96 条命令要逐条补元数据）。建议**先给 20 条核心命令打样**，其余分批补，未标注的取默认值（`group=其他`、`side_effect=read`）。

### B. 稳定性层：投入产出最高

#### B1. 元素库（Element Repository）

**现状**：定位信息散在每行参数里，界面一变全表崩，换机器要重录。

**方案**：逻辑名 → 多路定位器，脚本只写 `点击 登录按钮`，命中策略按优先级降级：

```
登录按钮 → [ 窗口相对坐标(0.3, 0.8)
            图像特征 login_btn.png
            OCR 文本 "登录"
            浏览器选择器 #login
            AI 描述 "蓝色的登录按钮" ]
```

**落点**：新增 `element_repo.py`；在 `commands.py` 的定位解析**之前**加一层「逻辑名解析」（参数若以 `@元素名` 开头则查库）。元素库面板与工作流操作库**同源**（同一份数据两个视图）。元素库随 `.acrpas` 打包分发。

**价值**：改界面只改一处；这是「换机器不重录」的唯一解。
**风险**：中。要小心「逻辑名 vs 字面参数」的歧义——建议用 `@` 前缀显式标记，不做隐式猜测。

#### B2. 定位自愈链（Self-healing）

**现状**：图像 / 窗口相对 / OCR / AI 四种定位法各自独立。

**方案**：串成降级链——图像未命中 → 窗口相对 → OCR → `ai_enhance.ai_find_element`，命中后把「降级路径」记日志并提示**固化为新特征**（写回元素库）。

**依赖**：**B1 元素库是前置**——自愈命中的结果要「固化回库」，没有库就没地方固化。两者必须一起做才有意义。

**价值**：把已有的 AI 视觉能力从「孤立命令」变成「日常兜底」。
**风险**：低。四种定位法都已存在，只是串起来 + 加日志 + 加固化。

#### B3. 断言命令组（P0，最推荐先做）

**现状**：`script_validate.py` 只做静态校验（不加载 tkinter 干跑），运行时没有「期望值」概念。

**方案**：补一组断言命令，失败走 `failure_policy`：

| 命令 | 用途 |
|---|---|
| 断言存在 | 元素 / 图像 / 窗口是否存在 |
| 断言文字 | OCR / 元素文本是否匹配 |
| 断言窗口 | 当前活动窗口是否为预期 |
| 断言变量 | `${var}` 是否等于 / 大于 / 包含 |
| 断言 HTTP 状态 | 配合网络命令 |
| 断言文件 | 文件是否存在 / 内容是否包含 |

**价值**：把「脚本跑完了」变成「业务结果对了」。配合已有 `--json-report` + `--exit-code`，直接支撑**回归测试与 CI 门禁**——这是企业敢用的硬指标。

**落点**：`commands.py` 新增命令组 + `script_validate.py` 补对应校验规则。
**风险**：极低。这是**全清单性价比最高的一项**，命令组 + 校验器，1–2 天可交付。

#### B4. 断点续跑

**现状**：`engine.py:1100` 的 `fail_context_*.json` 已存 row/vars/screenshot，但只能落盘。

**方案**：加「从失败行继续执行」——恢复变量快照 + 跳过已完成行。长流程（几百行对账）体验质变。

**依赖**：**D5 统一 run_id 是前置**——续跑要把「这次续跑」和「上次失败」关联到同一条链路，没有 run_id 无法判断「续的是哪一次」。
**风险**：中。变量快照恢复要处理「可变对象引用」和「外部状态已变」的边界，建议第一版只恢复标量变量 + 提示「文件/网络状态需自行确认」。

### C. 规模化层：单机 → 内网作业系统

#### C1. 事件型触发器（架构奖赏）

**现状**：`triggers.py` 的 `Trigger.poll(now)` 钩子已留、`time_based=False` 只被 `HotkeyTrigger` 用过（`triggers.py:207/523`）。

**方案**：新增「文件变化 / 窗口出现 / 进程启动 / 剪贴板变化 / HTTP Webhook」——**各只需 1 个类 + 1 行 `register()`**。

**价值**：改动面极小、收益极高，是插件化触发器架构的直接红利。
**风险**：低。注意事件型触发器**不参与 `next_run_at` 合并计算**（`time_based=False`），调度主循环要确认跳过它们的时间计算。

#### C2. 作业中心 UI

**现状**：`scheduler.py` 的 Task 已是统一模型（script/workflow/command + overlap/timeout/missed_run/max_runs）；`history.jsonl` 现成。

**方案**：只做一张面板——待执行队列、最近 50 次运行、失败重试、手动触发。**不必新建后端**。

**依赖**：**D5 run_id 是前置**——面板要把「一次运行」在四份产物里串起来展示。
**风险**：低。这是纯 UI 工作，且与上一份《定时调度与影子执行设计》里的「调度中心」是同一张面板。

#### C3. NetLink 加指标与编排

**现状**：`STATE_SYNC` / `LOG_TAIL` / `SCHED_STATUS` 只有状态，无 CPU/内存/队列/失败率；文件通道被 `.xls/.json/.acrpas` 白名单锁死。

**方案**：
1. 新增 `METRIC` 消息 + 拓扑视图（网页面板已有 API 骨架）；
2. `push_many` 之上加「批量执行 + 汇总回传」（fan-out / fan-in）。

**价值**：「一台机器盯整间机房」的完整闭环。
**风险**：中。fan-in 的**汇总回传**要定义「部分失败」语义（N 台里 M 台失败算什么），建议结果合约先行（见 §4 关联）。

### D. 工作流层

#### D1. retry / rollback / 子工作流引用

**现状**：子流程只能借 `script` 步骤递归 `.xls`；workflow.py:670 有「运行工作流」命令（脚本调工作流），但**工作流内部没有 `type: workflow` 步骤**。

**方案**：
- 步骤级 `retry` / `retry_delay`（复用 scheduler 的重试语义）；
- `rollback`：失败时执行补偿步骤（需命令元数据的 `side_effect` 才能判断「哪些步骤需要回滚」——**依赖 A3**）；
- 新增 `type: workflow` 步骤，工作流可引用工作流（嵌套深度限制 ≤3）。

**风险**：中。rollback 是**最难**的——UI 自动化天然不可回滚（点错了没法撤销），建议 rollback 只覆盖「可逆的副作用」（文件/变量），UI 操作明确标注「不可回滚」。

#### D2. 真并行

**现状**：`workflow.py` 的 `_run_parallel` 用锁串行化（牺牲并行度）。

**方案**：每分支独立变量作用域 + 结束合并（明确合并策略：冲突时**后写覆盖**还是**报错**，建议默认**报错并列出冲突变量**，最安全）。

**风险**：**高**。这是全清单最容易引入隐蔽 bug 的一项。真并行 + UI 自动化本身矛盾（两个分支同时抢鼠标）。**建议**：只对「纯计算/网络/文件」分支开放真并行，涉及 UI 的分支强制串行——用 A3 的 `side_effect` 字段自动判定。

#### D3. 工作流版本历史

**现状**：`version_manager.py` 只有 `.xls` 的 SQLite 版本库（`save_version(script_path, rows, ...)`）。

**方案**：扩展到 `.json` 工作流——`save_version` 的 `rows` 泛化为 `payload`（行列表 或 工作流 dict），按扩展名分流序列化。

**风险**：低。表结构加一列 `kind`（script/workflow）即可。

#### D4. 工作流撤销/重做

**现状**：脚本编辑有撤销/重做，工作流没有。

**方案**：复用脚本编辑的 undo 栈思路，对工作流的操作（增删步骤/改参数/连线）建命令栈。
**风险**：低。纯前端状态管理。

#### D5. 统一 run_id + 失败现场 UI（地基）

**现状**：`history.jsonl`、`fail_context_*.json`、CLI JSON 报告、日志各自为政，无统一 `run_id`。

**方案**：
1. 一次运行生成一个 `run_id`，**贯穿四者**（日志行 / history 记录 / fail_context 文件名 / CLI 报告）；
2. 失败现场从「只落盘」升级为**可查看 / 回放 / 两次运行对比**的 UI。

**价值**：这是**售后支持的杀手锏**——用户报「昨天跑错了」，一键调出当时的变量、截图、行号。
**风险**：低，但**必须在最早做**——它是 B4 断点续跑、C2 作业中心的前置。

### E. AI 深化层

#### E1. 工具调用闭环

**现状**：`ai_client.py` 单通道 `chat_completions`（`ai_client.py:46/60`），无 stream、无 function-calling。

**方案**：补 **流式 + function-calling**，形成「生成 → 校验 → 干跑 → 按错误自动修正」循环。`script_validate` 与静态检查就是现成的裁判。

**依赖**：**A3 命令元数据是前置**——function-calling 需要 `outputs` / `side_effect` 描述才能生成正确的 tool schema 与提示词。
**风险**：中。自动修正循环要设**最大轮次**（建议 3 轮）+ 每轮落盘中间产物，防止无限自我修改。

#### E2. 自然语言 → 工作流图

**方案**：AI 直接产出 `flow_graph` JSON，再用已有 9 项静态检查（不可达/孤立/悬挂出口/路径爆炸/环路复杂度）兜底。
**价值**：比「生成表格」更能体现差异化——表格人人能生成，**带控制流的图**才是 ACRPA 的主场。
**依赖**：flow_graph 静态检查已存在，可直接复用。
**风险**：低-中。生成的图必须**过静态检查才允许保存**，不过就退回让 AI 修。

#### E3. 成本与缓存

**方案**：token 记账、提示词/结果缓存、失败重试退避。
**价值**：企业落地必问的三个数（每次生成多少 token / 缓存命中率 / 失败率）。
**风险**：低。记账落 `history.jsonl`（复用 run_id）。

## 3. 优先级矩阵

| 优先级 | 条目 | 理由 |
|---|---|---|
| **P0（地基，先做）** | B3 断言命令组、D5 统一 run_id、A3 命令元数据 | 其它一切的前提；断言是「跑对了」的唯一判据 |
| **P1（稳定性 + 架构奖赏）** | B1 元素库、B2 自愈链、B4 断点续跑、C1 事件触发器、C2 作业中心 | 改动小收益大；元素库+自愈必须捆绑 |
| **P2（规模化 + 工作流）** | C3 NetLink 编排、D1 子工作流、D3 版本历史、D4 撤销重做 | 依赖 P0/P1；D2 真并行单独评估 |
| **P3（生态与 AI）** | A1 插件 UI 契约、A2 MCP Server、E1 function-calling、E2 NL→图、E3 成本缓存 | 战略价值高但依赖前面全部地基 |

**高风险项单独标注**：D2 真并行（UI 抢鼠标 + 变量合并冲突）、A2 MCP 写入工具（权限审计）。这两项**不要**排在前面，且必须带约束（真并行只放非 UI 分支；MCP 先只读）。

## 4. 路线图

```
第一期（地基，2 周）
  ├─ B3 断言命令组（6 条断言 + 校验规则）
  ├─ D5 统一 run_id（贯穿日志/history/fail_context/CLI）
  └─ A3 命令元数据（先给 20 条核心命令打样）
  验收：一次运行的 run_id 能在四份产物里对齐；断言失败能让 --exit-code 非零

第二期（稳定性，3 周）
  ├─ B1 元素库（element_repo.py + 逻辑名解析）
  ├─ B2 自愈链（降级 + 固化回库）
  ├─ B4 断点续跑（恢复变量快照 + 跳过已完成行）
  └─ C1 事件触发器（文件/窗口/进程/剪贴板/Webhook）
  验收：改一次界面只改元素库一处；长流程失败后能续跑

第三期（规模化 + 工作流，3 周）
  ├─ C2 作业中心 UI（队列 + 历史 + 重试 + 手动触发）
  ├─ C3 NetLink METRIC + fan-out/fan-in
  ├─ D1 子工作流引用 + retry
  ├─ D3 工作流版本历史
  └─ D4 工作流撤销/重做
  验收：一台机器能看到全网节点的执行状态与失败率

第四期（生态与 AI，4 周）
```

## 6. 不做什么（防跑偏）

1. **不在地基完成前做 AI 闭环**。没有命令元数据，function-calling 的 prompt 要手写维护 94 条命令的描述，注定腐烂。
2. **不对 UI 分支做真并行**。两个分支抢鼠标是确定性 bug，用 `side_effect` 自动卡住。
3. **不承诺 UI 操作可回滚**。rollback 只覆盖文件/变量，UI 操作明确标「不可回滚」。
4. **不一开始开放全部事件主题**。先冻结 5 个核心主题，契约稳定后再扩。
5. **不让 MCP 写入工具裸奔**。必须复用 NetLink 的权限分级 + 危险命令人工审批。
