# ACRPA 定时调度 × 影子执行 设计方案

> 版本：2026-11-05  
> 范围：`src/scheduler.py`、`src/triggers.py`、`src/dialogs.py`（计划任务管理）、`src/ui/settings/cards/sched.py`、`src/netlink/`  
> 结论针对三个问题：① 定时功能是否需要完善 ② 是否新建 tab 做任务编排 ③ 是否新建「影子执行」tab



---

## 0. 一句话结论

定时调度**不是"要不要完善"，而是"骨架已经到 L1、可信度还停在 L0"**——8 种触发器、6 项执行语义、错过补偿、排队、超时看门狗全都有，但任务跑完**不落账**：执行日志只在内存、脚本型任务状态永远停在"运行中"、失败不通知、无法重试。

因此建议：

| 问题            | 结论                                                                      |
| ------------- | ----------------------------------------------------------------------- |
| 定时功能要完善吗      | **要，但补的不是触发器，是"可信度"**——历史落盘 / 结果回写 / 重试 / 通知 / 依赖 / 并发治理                |
| 新建主窗口 tab 做编排 | **不建议**。改为把现有 780×520 的弹窗升级为独立「调度中心」窗口，内部再分页                            |
| 新建「影子执行」tab   | **不建议做成 tab**。影子是**任务级执行模式**（`exec_mode=shadow`）+ 调度中心里的一个视图；首版只做 S1 干跑 |

## 1. 现状盘点（按代码实证）

### 1.1 已经做得不错的部分

| 能力       | 实现                                                                                                                           | 评价                      |
| -------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| 触发器 8 种  | `triggers.py`：Once / Daily / Weekly / Interval / Countdown / Hourly / OnBoot / Hotkey，`register()` 插件化                       | 架构干净，加触发器 = 1 类 + 1 行注册 |
| 执行语义 6 项 | `scheduler.py:61` `_EXEC_DEFAULTS`：`on_overlap` / `timeout_sec` / `missed_run` / `missed_delay_sec` / `stop_hotkey` / `sync` | 该有的都有，且缺字段取默认，向后兼容      |
| 目标三型     | `_run_script` / `_run_workflow` / `_run_command`                                                                             | 脚本 / 工作流 / 单命令统一成 Task  |
| 错过补偿     | `_run_missed_compensation`，含 `(task_id, due)` 去重和 boot 触发器互斥                                                                 | 考虑得很细                   |
| 排队 / 超时  | `_PENDING_MAX_AGE=600`、`_arm_timeout` 看门狗                                                                                    | 有，但上限只留 1 条             |
| 任务库备份    | `state.save_config()` 写盘前备份 + 保留 N 份                                                                                         | 有                       |
| 表单四页签    | `dialogs.py:1737`（任务 / 计划 / 热键 / 执行）                                                                                         | 正交拆分正确                  |

**这套骨架的质量超出一般个人项目的水平**，所以问题不在"再加功能"，而在"账算不清"。

### 1.2 三个硬缺口（都有代码位置）

**缺口 A：脚本型任务的状态永远停在「运行中」**

```python
# scheduler.py:584  _run_script
_add_task_log(name, os.path.basename(target), "运行中", label)
state.filename = target
_root.after(0, _main_run_fn)      # 投递到主线程
return True                        # ← 到这里就结束了

# scheduler.py:732  _execute_task
task["last_result"] = "运行中" if ok else "失败"
```

全库搜索 `last_result` / `on_run_done` / `run_finished`，只有两处赋值（`scheduler.py:701` 超时、`:732` 投递），**没有任何执行结束回写钩子**。

后果：最常见的「定时跑脚本」任务，跑完之后 `last_result` 永远是「运行中」，除非它超时。用户打开任务管理，看到一排"运行中"，无法判断昨晚到底成功了没有。workflow / command 型虽然有线程内 `_add_task_log("完成")`，但同样不改任务字段，日志也只进内存。

**这是本次评审发现的最严重定时缺陷**——它使"定时执行"无法被信任，而信任是自动化工具的第一价值。

**缺口 B：执行日志只在内存，重启即丢**

```python
# scheduler.py:50
_task_logs = []          # 执行日志
# scheduler.py:548
if len(_task_logs) > 500: _task_logs[:] = _task_logs[-500:]
```

`get_task_logs()` 返回的是内存列表。进程退出后，昨晚 23:00 那次失败的原因、截图、耗时全部消失。用户问"昨天为什么没跑"，系统答不出来。

**缺口 C：全局串行，同时到期的任务互相 skip**

```python
# scheduler.py:807
if state.running:
    if overlap == "queue": ...   # 排队上限 1，超出丢最旧
    elif overlap == "terminate": ...
    else: skip                    # 默认
```

`state.running` 是进程级单例。9:00 有 5 个任务同时到期 → 第 1 个跑，其余 4 个按 `skip` 直接跳过并只写一条内存日志。批量场景（10 个门店各一个任务）下这是致命限制，且用户很难察觉——不报警、不重试、下一次要等到明天。

### 1.3 其它可改进项

- **无重试**：失败即等下一个周期。UI 操作类脚本失败往往一次重试就能过。
- **无依赖**：`depends_on` / `on_success` / `on_fail` 全无，做不到"跑完 A 再跑 B，A 失败则跳过 B"。
- **无失败通知**：失败只写日志。人不在电脑前就等于没发生。
- **无脚本漂移检测**：`target` 是裸路径，脚本改名/移动后任务静默失效，只在触发时记一条"脚本不存在"。
- **无结果产物**：任务跑完只有"完成/失败"，没有「处理 812 行 / 失败 3 行」这种可核对的数字。
- **`sync` 字段是半成品**：`_EXEC_DEFAULTS` 里有，`add_task` 不写入，也无处读取。
- **轮询 30s（下限 5s）**：分钟级够用，但秒级场景（配合扫码枪、Webhook）不够。

## 2. 定时功能该补什么（按"可信度"排序）

不要按"功能多寡"排，按"用户敢不敢把活交给它"排。

### P0 — 让定时「可被信任」（建议下一个版本全做）

| #    | 项目            | 落点                                                                    | 说明                                                                                                                     |
| ---- | ------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| P0-1 | **执行结果回写**    | `main_run` 结束路径 + `scheduler.mark_run_finished(task_id, ok, detail)`  | 给 `state` 加 `current_task_id`，脚本结束（含异常/手动停止）时回写 `last_result` / `duration` / `run_count`，并写一条持久日志。**修完这一条，"运行中"假象才消失** |
| P0-2 | **执行历史落盘**    | 新增 `src/run_history.py`，追加写 `%APPDATA%/ACRPA/runs/YYYY-MM.jsonl`      | 只追加不改写，天然并发安全、可 grep、可导出；按任务与时间双索引；保留 90 天。比 SQLite 轻，符合便携原则                                                           |
| P0-3 | **失败重试 + 退避** | 任务字段 `retry` / `retry_delay` / `retry_backoff`，在 `_after_fire` 后挂重试队列 | 默认 0 次（保持现状），UI 提供 1/2/3 次预设。重试也要落账，避免"重试成功但日志显示失败"的误解                                                                 |
| P0-4 | **失败通知**      | 新增 `src/notify.py`：托盘气泡（必有）+ Webhook（企微/钉钉/飞书机器人，可选）                  | 只对「连续 N 次失败」和「从未失败突然失败」告警，避免噪音。这是"人不在电脑前"场景的唯一解                                                                        |
| P0-5 | **并发治理**      | 要么明确串行队列并显示排队位置，要么放开进程级并发                                             | 推荐先做前者：全局任务队列 + 队列位置可视 + 排队超时告警。真并发需要重写 `state.running` 语义，风险大，放 P1                                                    |
| P0-6 | **脚本漂移检测**    | 任务存 `target_hash`，启动与定时扫描比对                                           | 改名 → "路径失效"；改内容 → "脚本已变更（哈希不符），请确认"，给一键"接受新版本"。防止"跑了两周才发现跑的是旧逻辑"                                                       |

### P1 — 让定时「好用」

|   |   |   |
| - | - | - |

- **依赖编排**：`depends_on: [task_id]` + `on_dep_fail: skip|run|notify`。有了它，"采集 → 清洗 → 上传"才能串起来。**注意：只做线性链 + 简单扇出，不要做通用 DAG 画布**（见 §5）。
- **日历视图**：调度中心里 month/week 视图，"哪天没跑"一眼看到。列表答不了这个问题。
- **任务模板与批量克隆**：`{{门店}}` 占位符 + 一次生成 N 个任务。10 个门店手点 10 次是当前真实痛点。
- **停机日历**：法定节假日 / 维护窗口，避免节假日刷数据。
- **结果合约**：任务声明 `outputs`，脚本结束时产出 `{"rows": 812, "failed": 3}`，写进历史。**这是"证明做对了"的关键**（见 §4 D2）。

### P2 — 锦上添花

- cron 表达式导入/导出（给习惯 crontab 的用户，纯便利，不作卖点）
- 任务即代码：`tasks/*.yaml` 与 GUI 双向同步（团队协作、Git 版本化）
- 秒级触发器（配合事件总线）

## 3. 要不要新建 tab 做任务编排

### 3.1 三个方案

| 方案               | 形态                            | 优点                         | 代价                               | 判断       |
| ---------------- | ----------------------------- | -------------------------- | -------------------------------- | -------- |
| **A** 主窗口新 tab   | notebook 加「调度」页               | 入口最短                       | 与现有架构方向相反；主窗口 tab 已有懒加载/换肤/快捷键耦合 | ✗        |
| **B** 独立「调度中心」窗口 | 升级 `open_sched_manager`，内部再分页 | 可最大化/第二屏常开；刷新不干扰编辑器；复用现有窗口 | 需重写该弹窗（约 500 行）                  | **✓ 推荐** |
| **C** 保持现状弹窗     | 780×520 列表                    | 零成本                        | 装不下编排、历史、影子、诊断                   | ✗（仅短期）   |

### 3.2 为什么不是主窗口 tab

三条实证理由：

1. **架构方向相反**。当前主窗口 notebook 只有两个 tab：`编辑`（`ui_editor_view`）和 `工作流`（`ui_workflow_view`，还是懒构建）。**设置页正是从 tab 拆成独立窗口的**（`ACRPA.py:6583` 注释："设置已分离为独立窗口，不再占用 Tab"）。再往 notebook 加一个低频配置页，是在回退一次已经被验证正确的重构。
2. **刷新模型冲突**。调度中心需要"常驻刷新"——任务状态、下次执行倒计时、队列位置、影子差异。塞进 notebook 意味着用户不切过去就不刷新，切过去又要处理懒构建。独立窗口可以用 `after()` 自管刷新节奏，与编辑器零耦合。
3. **占用需求不同**。编排（时间轴、依赖连线、历史表格、影子 diff）要横向空间。用户会**开着它盯执行**——这是第二屏场景，不是 tab 场景。

### 3.3 推荐形态：调度中心（独立窗口，内部 5 页）

```
src/ui/sched_center/
├── window.py       # 壳：标题栏 + 状态条（总开/暂停/下次到期）+ 内部 Notebook
├── page_tasks.py   # ① 任务：列表 + 分组 + 内联启停 + 搜索
├── page_editor.py  # ② 编排：任务详情（复用 dialogs._sched_task_dialog 的四页签）
├── page_history.py # ③ 历史：时间线 + 按任务筛选 + 失败堆栈 + 耗时趋势
├── page_shadow.py  # ④ 影子：影子运行列表 + 与真实运行 diff
└── page_diag.py    # ⑤ 诊断：调度线程状态/轮询间隔/漂移告警/日志导出
```

**第一版只做 ①②③⑤（约 3–4 天），第 ④ 页留空占位**，等 S1 干跑落地后再填。理由：先把"账算清"（P0-1/2）做出来，影子才有比对对象——没有真实运行历史，影子差异无处附着。

入口统一：托盘菜单（已有）、设置卡「管理计划任务」（已有）、快捷键。

## 4. 影子执行怎么设计

### 4.1 先把"影子"拆成三档（成本差 10 倍）

| 档                      | 语义                                                                                      | 需要什么                                                                                      | 成本    | 建议时机     |
| ---------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----- | -------- |
| **S1 干跑**<br />dry-run | 不点鼠标不输入，只做**静态可执行性推演**：命令是否存在、参数是否合法、变量能否求值、图片/元素能否定位、文件路径是否存在 → 输出「动作清单 + 风险分级 + 预计耗时」 | 复用 `commands` / `script_validate` / `interp` / `ocr_backend` / `ai_find_element`，**零新依赖** | 1–2 天 | **先做这个** |
| **S2 沙箱实跑**            | 在隔离环境真跑一遍，比对结果                                                                          | 影子机（VM 或 NetLink 节点）+ 环境快照                                                                | 1–2 周 | v0.6     |
| **S3 并行比对**            | 生产跑的同时影子跑，比对**操作序列**与**结果产物**，差异告警                                                      | S2 + 操作序列录制 + 结果合约                                                                        | 2–4 周 | v1.0     |

**关键判断**：用户说的"影子执行预设"如果一开始就按 S2/S3 做，几乎必然烂尾——它需要第二台机器、环境同步、结果定义，任何一个没到位就出不了结论。**S1 才是最小闭环**：它甚至不需要新窗口，一个 `--dry-run` 就能回答"这脚本今晚大概率能不能跑通"。

### 4.2 S1 干跑流水线（可直接实现）

```
输入：脚本路径（或任务 target）
  ↓
① 解析      script_io 载入命令表 → [(cmd, args)]
② 命令校验  cmd ∈ commands 注册表？参数个数/类型？      → 致命
③ 变量求值  遍历 ${var}，按 interp/safe_eval 求值      → 致命（未定义）
④ 目标可解  图像/元素/OCR 目标能否在当前屏幕定位      → 警告（最易变）
⑤ 资源检查  引用的图片/文件/工作流是否存在            → 警告
⑥ 风险评级  纯坐标点击无回退 / 无等待 / 循环无上限 / 无超时  → 提示
输出：JSON + 人类可读报告
```

每一步都是**只读**：不点击、不输入、不改文件。可以无头跑（`run.py --dry-run script.acrpas --json`），也可以挂到任务上。

**必须避免的错误设计**：不要输出「通过 / 不通过」二元结论。UI 自动化天然有不确定性（动态界面、网络等待），二元结论会把大量可跑通的脚本判死，用户两次之后就再也不用了。**输出风险分级（致命 / 警告 / 提示）并给出"预计成功率区间"**，让用户自己决定。

### 4.3 数据模型

任务上新增三个字段（都向后兼容，缺字段 = 现状）：

```python
task["exec_mode"]    = "real" | "shadow"   # 默认 real
task["shadow_of"]    = task_id             # 影子任务指向的真实任务
task["shadow_policy"] = "report" | "block" # 影子失败时：仅报告 / 阻止真实任务
```

影子运行不写 `last_run_at` / 不递增 `run_count` / 不消费一次性触发器——它必须与真实运行**账目隔离**，否则统计全乱。这条要在 `_fire_task` 里显式分支，不能靠 `run_task_now(advance=False)` 凑合（那个仍会改 run_count）。

### 4.4 UI：不是 tab，是「徽标 + 视图 + 比对」

| 位置         | 做法                                                                 |
| ---------- | ------------------------------------------------------------------ |
| 任务列表行      | 影子任务行加 `◑` 徽标 + 灰色文字；真实任务行若存在影子结果，显示 `影子: 3 警告` 小徽标                |
| 调度中心 ④ 影子页 | 上半：影子运行列表（时间 / 任务 / 风险数 / 结论）；下半：选中项的风险明细                          |
| 比对面板       | 同一任务「上次真实运行」vs「本次影子运行」并排：动作数、耗时、风险项差异。**这才是"影子"真正的价值——差异，而不是单次报告** |

**为什么不做成 tab**：影子必须与真实任务**成对出现**才能读懂。做成独立 tab，用户看到的是"一堆孤立报告"，失去了比对语境；而且会让"影子"看起来像第三种执行方式（脚本 / 工作流 / 影子），实际它是**正交于任务类型的执行模式**。

## 5. 发散：值得考虑的新功能

按"值得做"排序，不是按酷炫程度。

| #       | 功能            | 一句话                                                                  | 价值                                           | 成本 |
| ------- | ------------- | -------------------------------------------------------------------- | -------------------------------------------- | -- |
| **D1**  | **事件触发器总线**   | 文件到达 / Excel 被改 / 邮件到达 / Webhook / 扫码枪输入 / 剪贴板变化 → 触发任务              | 把"定时"升级为"随时"，是触发器架构的自然延伸（`triggers.py` 只需加类） | 中  |
| **D2**  | **结果合约 + 断言** | 任务声明 `outputs`，脚本结束产出 `{"rows":812,"failed":3}` 并断言 `failed==0`      | 从"跑完了"到"跑对了"，是企业敢用的前提                        | 低  |
| **D3**  | **失败自动取证包**   | 失败瞬间自动打包：截图 + 变量快照 + 前后 200 行日志 + 当前窗口树 → `evidence/<task>/<ts>.zip` | 排查从"猜"变"看"，复用已有失败现场能力                        | 低  |
| **D4**  | **执行时长漂移告警**  | 记录每次耗时，超均值 3σ 或连续 3 次上升 → 告警                                         | 界面变慢、元素加载变长是失败前兆，**能提前 3 天发现问题**             | 低  |
| **D5**  | **任务租赁锁**     | 多机同任务只跑一次（NetLink 内已有节点，可做轻量文件锁/Redis 协议）                            | 多台机器共用任务库时的必备                                | 中  |
| **D6**  | **危险任务审批**    | 含"删除/上传/支付"命令的任务，执行前需人工确认（托盘弹窗 / 企微卡片）                               | 半自动场景刚需；也让审计有话说                              | 中  |
| **D7**  | **调度即代码**     | `tasks/*.yaml` ⇄ GUI 双向同步，可 Git 版本化、Code Review                      | 团队协作；也让"配置漂移"可追溯                             | 中  |
| **D8**  | **影子对账（S3）**  | 生产与影子并行，比对操作序列与结果                                                    | 见 §4.1                                       | 高  |
| **D9**  | **任务数字孪生**    | 基于历史，预估"这次改动会影响多少任务/多少行数据"                                           | 改脚本前的安全感，很讨喜但优先级低                            | 高  |
| **D10** | **时间机器回放**    | 用历史运行记录重放某次执行（含当时的变量快照）                                              | 复盘神器；依赖 D3 的取证包                              | 高  |

**其中我最看好 D2 + D4**：都不是新功能，而是**把已有数据变成判断力**。D2 让"成功"有定义，D4 让"要出事"有预警——两者加起来成本不到一周，却直接回答"这工具靠不靠得住"。

## 7. 不做什么（防止跑偏）

1. **不做通用 DAG 可视化画布**。ACRPA 的任务依赖关系天然是浅的（链 + 扇出）。一个能拖动、能连线的画布，开发成本是线性依赖的 5 倍，使用频率是 1/10。用「列表 + 上/下游」两个下拉就够。
2. **不把 cron 表达式当卖点**。真正的差异在"跑对了没有"，不在"能不能写 `*/5 * * * *`"。
3. **不做云调度**。ACRPA 的立身之本是内网、便携、零依赖。云端调度会把这三条同时毁掉。
4. **不把影子执行做成独立 tab 或独立产品**。它是执行模式，不是第三个物种。
5. **不在没有历史数据前做任何"智能预测"**。D9 数字孪生、AI 排程这类，没有 3 个月真实运行记录全是幻觉。
