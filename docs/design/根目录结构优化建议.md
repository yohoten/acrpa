# 根目录结构优化建议

> 实测时间：2026-11-02 · 对象：`D:\CodingEmber\ACRPA` · 方法：`ls`/`du`/`git ls-files`/`git count-objects` + 源码交叉核对
> 本文只谈**仓库根这一层**。`src/` 内部的平铺、循环依赖、tkinter 污染问题见 [`项目结构优化建议.md`](项目结构优化建议.md)。
> 本文给动因与方案；**强制性条款**（必须/应当/禁止）与机器检查见 [`根目录规范.md`](根目录规范.md)。

---

## 一、结论摘要

三条判断，按重要性排序：

1. **根目录的问题不是"文件太多"（38 项，尚可接受），而是五种性质不同的东西挤在同一层**：源码入口、发布资产（落地页）、文档、构建产物、运行时状态。混在一起导致 `.gitignore` 只能用大量 `!` 例外来打补丁，而补丁已经出现失效。
2. **最该先动的不是搬目录，而是两件"配置已经错了但没人发现"的事**：`ACRPA.spec` 白名单失效（`!ACRPA.spec` 匹配不到实际文件名），`.gitattributes` 名不副实且根本未纳管（LFS 规则从未生效）。这两件修复成本低、收益确定。
3. **目录级搬迁放到最后做**。根目录搬迁的收益主要是"看起来整齐"，风险却落在打包路径（spec 的 `pathex`/`datas`）、`DATA_ROOT` 语义、GitHub Pages 源目录上。真正影响开发效率的是 `src/` 与 `tools/` 的内部结构，不是根这一层。

## 三、问题清单（按修复性价比排序）

### P0-1 运行时状态散落 8 处，且落点规则不统一

**现状**：`state.py:353` 早已建立数据根抽象 —— `DATA_ROOT = userdata/ if PORTABLE else APP_DIR`，`config.json`、`logs/`、`screenshots/`、`backups/`、`script_versions.db` 都走它。但有三处漏网：

| 位置 | 实际落点 | 应为 |
|---|---|---|
| `src/ui/exec_bar.py:519,561` | `APP_ROOT/recent.json`（`ACRPA.py:6159` 注入 `app_root=APP_ROOT`） | `DATA_ROOT/recent.json` |
| `src/ui/workflow_view.py:1399` | `APP_ROOT/recent_workflow.json` | `DATA_ROOT/recent_workflow.json` |
| `src/single_instance.py:107` | 异常兜底 `os.getcwd()/.ipc_key` | `state.APP_DIR/.ipc_key` |

**后果**：

- 便携模式下 `config.json` 进了 `userdata/`，但两个"最近使用"列表仍写在程序目录根 —— **U 盘拔走后这些状态不会被带走**，与便携语义直接冲突。
- `os.getcwd()` 兜底意味着从快捷方式、其他工作目录、任务计划程序启动时，`.ipc_key` 会写到意外位置，单实例互斥随之失效（第二个实例拿不到同一 token，会重复启动）。
- 非便携模式下这 8 项持续污染程序目录根，用户视角"解压即用"变成"解压后根目录变乱"。

**建议**：在 `state.py` 增加唯一入口 `data_path(name)`，五个调用点改为经它取路径；`single_instance` 兜底改 `state.APP_DIR`。收益是可验证的（便携模式 `userdata/` 完整性可用一条断言检查），成本约 6 处改动。

### P0-2 `ACRPA.spec` 白名单已失效，且文件名含空格

**现状**：

- `build.py:16-17`：`APP = "ACRPA v{}".format(_VER)`；`build.py:319`：`spec = BASE/{APP}.spec` → 实际产物 **`ACRPA v0.1.30-beta.spec`**（带空格、带版本）。
- `.gitignore` 仍写着 `*.spec` + `!ACRPA.spec`（并附注释"ACRPA.spec 目前作为例外纳管"）。
- `git status` 显示 `D ACRPA.spec`（已被删除），磁盘上是新版带版本号的、未纳管且匹配 `*.spec` 被忽略。
- `build.py:317-320` 的 `clean()` 只删当前版本名的 spec → 换版本后**旧 spec 永久残留**在根目录。

**后果**：白名单永久失效；每发一次版根目录多一个带空格的文件（对 CI/脚本是引号陷阱）；仓库里那份 spec 与真实构建产物早已分叉，谁读谁错。

**建议（二选一）**：

- **方案 A（推荐）**：spec 固定名 `ACRPA.spec`，版本只体现在 EXE 的 `name=` 字段内。同时删掉 `.gitignore` 的 `!ACRPA.spec` 例外，spec 彻底不纳管（它由 `build.py` 每次重建，纳管只会产生噪声）。`docs/design` 与 `README` 里提到 spec 的地方同步改。
- **方案 B**：保留版本名但去空格（`ACRPA-v0.1.30-beta.spec`），白名单改 `!ACRPA-v*.spec`，`clean()` 改为通配删除 `ACRPA*.spec`。比 A 多维护一套通配规则，收益仅是"能看出是哪版构建"。

### P0-3 `.gitattributes` 名不副实，且未纳管

**现状**：

- 文件 1631 字节、31 行，其中 **30 行是注释**，真实规则只有 1 条：`lib/paddle_ocr/*.dll filter=lfs …`。
- `git ls-files --error-unmatch .gitattributes` → 报错"did not match any file(s) known to git"，**该文件从未被提交**。
- 注释声称 `lib/paddle_ocr/*.dll (~196 MB)`；实测 `lib/paddle_ocr/` 全部内容 **920 KB**（`PaddleOCR.dll` 903 KB + `PaddleOCRSharp.dll` 29 KB）。`git lfs ls-files` 输出为空。
- 结果是：**真正的换行/二进制属性规则一条都没有**（`*.bat`、`*.xlsx`、`*.dll`、`*.png` 全按 git 默认处理），而那条 LFS 规则从未对任何 clone 生效。

**后果**：跨平台/CI 上 CRLF 漂移无人兜底；注释里的过期体积数据（196 MB vs 920 KB）会误导后续"要不要上 LFS"的决策 —— 按实测数据，这个决策的答案已经是不需要。

**建议**：拆成两件事 ——

1. 把这份备忘内容迁到 `docs/design/lib-LFS迁移备忘.md`（或直接删除，因为前提"196 MB"已不成立）；
2. 新建**真正的** `.gitattributes` 并提交：
   ```gitattributes
   * text=auto eol=lf
   *.bat  text eol=crlf
   *.cmd  text eol=crlf
   *.ps1  text eol=crlf
   *.png  binary
   *.ico  binary
   *.dll  binary
   *.xls  binary
   *.xlsx binary
   *.db   binary
   ```

### P1-4 `template/` 与 `res/template/` 双轨，且 ignore 与纳管自相矛盾

**现状**：

| 目录 | 角色 | 证据 | 状态 |
|---|---|---|---|
| `res/template/` | **随包只读**模板（56 KB xlsx） | 生成器 `tools/gen_script_template_xlsx.py:47`；`src/help_window.py:67` 读取 | 正常 |
| `template/` | **用户可写**示例库（片段库） | `src/snippets.py:29-40`：`state.SNIPPET_DIR` 优先，空则回落 `<app_root>/template`，并 `makedirs` | 混乱 |

矛盾点：

- `.gitignore` 有整目录规则 `template/`，但目录下 **12 个文件已被跟踪**（ignore 对已跟踪文件无效）→ 后果是：**新增示例模板永远加不进来**，而修改仍会产生 diff。
- 目录内混入了运行时产物：`脚本模板.xls`（13.8 KB）与 `脚本模板.xls.bak`（13.8 KB），均为 2026-11-02 09:06 由程序写出，时间戳与其余 9 月示例明显不同类。
- 用户可写目录与随包资源同名概念（"template"），升级/卸载时语义不清；`.bak` 有被片段库当示例列出的风险。

**建议**：

1. `template/` → `samples/`（根目录一级，作为用户可写的示例库），`state.SNIPPET_DIR` 默认值同步改；
2. 运行时写出的 `脚本模板.xls` / `.bak` 改落 `DATA_ROOT`；
3. `.gitignore` 删掉 `template/` 整目录规则，改为 `samples/*.bak`；
4. 迁移后加断言：`git ls-files samples` 数量 > 0 且不含 `.bak`。

### P1-5 `tools/` 职责混杂，`tests/` 迁移停在半路

**现状**：

- `tools/` **80 项 / 7.9 MB**：**55 个 `_` 前缀**一次性脚本（`_debug_*`、`_probe_*`、`_publish_release_github_0129*.py`、`_recreate_release_github2.py` 等）+ **15 个常驻工具**（`bump_version.py`、`run_tests.py`、`export_command_schema.py`、`make_release.py`、`publish_release.py`、`gen_script_template_xlsx.py`…）。
- `tests/` 已建成（**79 个 `.py` / 1.4 MB**），且 `tools/_test_*.py` 已清零 —— 说明迁移做了一半，只搬了测试。
- 子目录：`_smoke_result_phase1`(27 文件)、`_smoke_result_regression`(42)、`_smoke_result_regression2`(42) **共 111 个结果文件、572 KB 仍被纳管**；而 `.gitignore` 只忽略了 `_smoke_result_phase2/` 与 `_ui_screenshots/` —— 同一类产物三种待遇。
- CI 执行 `python -m compileall -q src tools`（`.github/workflows/ci.yml:41`）→ **一次性排查脚本与结果目录也在被编译**，一旦某个 `_debug_*.py` 语法腐烂，CI 直接红，与项目质量无关。

**建议**：按"是否需要长期维护"二分，而不是按文件名前缀：

```text
tools/
├── ci/          # CI 调用的入口：run_tests.py、static_checks.py、check_toc.py
├── build/       # build 链路：build.py 辅助、clean_before_build.py、safe_build.py、rebuild_all.py
├── gen/         # 生成器：export_command_schema.py、gen_script_template_xlsx.py、benchmark.py
├── release/     # 发版：bump_version.py、make_release.py、publish_release.py、verify_release.py
├── probe/       # 一次性排查脚本（允许腐烂，不进 compileall）
└── _out/        # 所有 _smoke_result_* 与截图产物，整目录 ignore
```

配套：`ci.yml` 的 `compileall` 只编 `src` 与 `tools/{ci,build,gen,release}`。

### P2-6 文档三处重叠

**现状**：`README.md`（51 KB，含 94 条命令全表 + FAQ + 结构树）、`使用说明.md`（15 KB，**再列一遍命令清单**）、`docs/`（47 个 md，已分 `analysis/ archive/ design/ releases/`，但根下仍平铺 **14 个 md**：`netlink-*` 8 个、`浏览器使用说明`、`浏览器后端增强设计`、`python扩展使用说明`、`marketplace-v2-使用说明`、`paddle-ocr-dll-使用说明`、`执行控制tab设计方案`）。

**后果**：命令数从 68 → 88 → 92 → 94 的每次变更都要改三处，本轮之前已经出现过 README 落后于 schema 的情况；`docs/` 根下 14 个文件里"用户手册"（使用说明类）与"设计文档"（设计方案类）混放，分类刚建好却没用上。

**建议**：

- 命令表**只保留 README 一处**；`使用说明.md` 降级为 `docs/guide/快速上手.md`，删掉命令清单章节（改为指向 README 锚点），避免第三份副本继续漂移。
- `docs/` 根只留一个索引（或空），把 14 个文件归位：`*使用说明.md` → `docs/guide/`；`*设计*.md` → `docs/design/`；`netlink-*` → `docs/design/netlink/`。

### P2-7 构建产物 1.06 GB 常驻

`dist/` 445 MB + `build/` 169 MB + `.venv/` 64 MB + `.git/` 385 MB = **1.06 GB / 1.1 GB（96%）**。前两者可随时回收（`build.py` 的 `clean()` 已实现）；`.git` 385 MB 里 `size-pack` 185.9 MB，说明历史里有大二进制（paddle DLL、旧 exe）。清理建议：先 `python build.py --clean` 回收 614 MB；`.git` 瘦身需 `git gc --aggressive` 或重写历史，属于破坏性操作，团队协作前需对齐，暂不建议。

---

### P2-8 缺 `config.example.json`

`config.json` 被 `.gitignore` 忽略（4.3 KB），新人 clone 后没有任何配置样板；FAQ 里"设置 → AI 增强填 `api_key`"无法对照键名。建议从当前 `config.json` 脱敏后生成 `config.example.json` 并纳管（键名 + 注释，值留空/占位），README 补一句引用。

## 五、分阶段落地

| 阶段 | 动作 | 涉及文件 | 风险 | 验收 |
|---|---|---|---|---|
| **P0-a** 状态收敛 | 新增 `state.data_path()`；5 处调用点改走它；IPC 兜底改 `APP_DIR` | `state.py`、`ui/exec_bar.py`、`ui/workflow_view.py`、`single_instance.py` | 低。路径变更后旧 `recent.json` 需一次性迁移（可加兼容读：新路径不存在则读旧路径） | 便携模式下 `userdata/` 含 `recent*.json`；从其他目录启动仍单实例 |
| **P0-b** spec 归位 | 采用方案 A：固定名 `ACRPA.spec`；`clean()` 通配删除；删 `.gitignore` 例外 | `build.py`、`.gitignore`、`docs/`、`README` | 低。仅影响本机构建脚本 | 连跑两次 `build.py` 后根目录只余 0 个 spec；`git status` 干净 |
| **P0-c** 属性文件 | 备忘迁出，写真正的 `.gitattributes` 并提交 | 新增/删除 2 文件 | 低。首次提交可能触发一次行尾规范化 diff，建议单独一个 commit | `git check-attr -a -- README.md` 有 `text`；`*.bat` 为 `eol=crlf` |
| **P1-a** template 拆分 | `template/` → `samples/`；运行时写出改 `DATA_ROOT`；ignore 规则替换 | `snippets.py`、`state.py`、`.gitignore`、目录重命名 | 中。片段库默认目录变了，需保留一个版本的回落兼容 | `snippets.py` 在无 `SNIPPET_DIR` 时落到 `samples/`；`git ls-files samples` 无 `.bak` |
| **P1-b** tools 分类 | 建 5 个子目录，移动 15 个常驻工具与 55 个一次性脚本；结果目录归 `_out/` 并 ignore | `tools/**`、`ci.yml`、`README` 开发约定段 | 中。所有引用 `tools/xxx.py` 的地方（CI、README、文档）都要同步 | `grep -rn "tools/run_tests" .` 全部指向新路径；CI 绿 |
| **P2** 文档与清理 | 使用说明降级、docs 根归零、`config.example.json`、清 dist/build | 文档若干 | 低 | README 内部链接 0 失效；`du -sh .` 降到 ~500 MB |

建议顺序：**P0 三步一次性做完（同一批提交）→ P1 分两次 → P2 随缘**。P0 的三件事互不冲突，且都不动目录位置，是纯收益项。

## 六、不建议做的事

| 想法 | 为什么不做 |
|---|---|
| 把 `index.html` / `img/` 挪进 `docs/` | GitHub Pages 的 source 目录要改配置；`img/*.png` 相对路径全部断裂；两个 150 KB 文件挪走后根目录并不会"变干净"，只是把复杂度转移 |
| 给 `run.py` 套一层 `main.py` 包装 | `run.py:1` 起就是"判决 + 分流"的唯一入口，`--rollback` / `--exec-task` / IPC 分支都依赖它被直接执行；套壳会让更新器与打包路径各多一层间接 |
| 把 `src/` 平铺内容提到根 | import 路径、spec 的 `pathex`、`DATA_ROOT`（按程序目录算）全部连带失效，是收益最低、风险最高的一项 |
| 为"整齐"重命名 `res/` → `assets/`、`lib/` → `vendor/` | git 不追踪 rename，历史会断；且 `res/` 已被 spec 的 `datas` 与 `help_window.py` 硬编码，改名需全量替换字符串 |
| 现在就给 `lib/paddle_ocr` 上 Git LFS | 实测仅 920 KB，注释里的 196 MB 已过时。LFS 会增加 clone 步骤与 CI 依赖，收益为负 |

## 七、可直接执行的验收命令

# 3. spec 与 gitattributes 是否纳管（P0-b/P0-c 后应为 0 / 1）
git ls-files "*.spec" | wc -l
git ls-files .gitattributes | wc -l

# 4. ignore 与纳管是否矛盾（目标：无输出；当前 12 个 template/ 文件）
git ls-files -i -c --exclude-standard

# 5. 仓库体积
git count-objects -vH | grep size-pack
du -sh .git dist build

第 4 条是本次发现的**通用检测手法**：`git ls-files -i -c` 会列出"既被跟踪、又匹配忽略规则"的文件 —— 当前 `template/` 下的 12 个文件就属于此类，这类矛盾是 `.gitignore` 长期打补丁的典型副作用。
