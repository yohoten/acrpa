=== v0.1.26 新增功能 ===

软件更新机制重构（本次重点）：
- 修复打包后版本号失真：此前版本号只从项目根目录读取，打包成 EXE 后必然读不到而回退到
  内置值，导致「关于」页与更新判断永远停留在旧版本。现按 EXE 同级目录 → 内嵌副本 →
  项目根目录依次查找，并让打包过程带上 VERSION 文件。
- 检查更新改为多源降级：GitHub Releases → raw.githubusercontent → jsDelivr → Gitee，
  任一可用即返回；不再因单个地址不可达就把网络错误当成「已是最新」。
- 某个来源报出的版本不比本机新时不会立刻收工，而是继续探测其余来源取版本最高者 ——
  避免某个镜像缓存落后（实测 jsDelivr 的分支别名与 Gitee 镜像都会滞后）把真实存在的
  新版本静默吞掉。
- 网络传输改为双栈：requests 因证书校验失败时自动改用系统证书库重试。在启用 TLS 拦截的
  企业网络里，requests 自带的证书包验不过代理自签证书，而系统证书库可以 —— 只走 requests
  会让两个权威来源永久不可达。
- 版本比较支持 v 前缀、位数不齐与预发布后缀（0.1.26-beta 现能被正确判为低于 0.1.26）。
- 检查结果区分「已是最新 / 网络故障 / 清单损坏」，网络问题只写日志，不打扰正常使用。
- 新增应用内更新窗口：状态栏「新版本 vX.Y.Z 可用 — 点击更新」→ 查看更新内容 →
  下载（显示进度与体积）→ 自动校验 sha256、体积与 ZIP 格式 → 一键重启更新。
- 便携版一键自更新：程序退出后由独立助手校验包内版本号，并以 .new 文件中转原子替换
  主程序与 VERSION，随后自动重启。只替换主程序，配置、脚本、模板、日志一律不动。
- 下载直链可在 VERSION 文件中声明多条（按顺序逐个尝试）；未声明时按 GitHub Release
  约定自动推导（同时兼容 v0.1.26 与 v0.1.26.0 两种 tag 写法）—— 此后发版只需改版本号。
- 下载完成后会复核包内 VERSION，镜像返回旧包时自动换源，而不是装错版本；
  VERSION 未配置 sha256 时不会使用不带版本信息的仓库内 dist/ 兜底通道，宁可报错也不
  静默装上旧包。
- 更新包统一存放于程序目录 updates/ 下，保留最近一个，其余自动清理。

更新入口：
- 启动 3 秒后自动检查（可在「设置 → 系统」关闭），有新版时点击状态栏提示
- 「设置 → 快速操作 → 关于 ACRPA → 检查更新」

发版流程（维护者用）：
- python tools/bump_version.py --patch   递增版本号（同时同步 VERSION 与 README 版本标记）
- python build.py --clean                打包
- python tools/make_release.py --write-sha256   生成发布包 + 回填 sha256 + 生成 Release 说明
- python tools/publish_release.py --exe  建草稿 Release → 上传附件 → 发布（一条命令）
- python tools/make_release.py --no-zip --purge-cdn main   清 jsDelivr 分支别名缓存
  注意：本仓库启用了 release 不可变 —— 附件必须在草稿阶段上传，已发布的 Release 无法再改；
  且被已发布 Release 占用过的 tag 不可复用（报 tag_name was used by an immutable release），
  故 tag 由工具从 VERSION 的直链推导，本版为 v0.1.26.0，不要手工拼 v<版本号>。
  Gitee 镜像需单独 push，且其 raw 路径对 dist/ 下大文件返回 403，仅作最后兜底。
